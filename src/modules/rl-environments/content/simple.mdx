## The big picture

An AI agent is a program that uses tools to finish a job. The tools might be a search box or a
database. The agent works over several steps instead of answering in one go.

One way to improve an agent is to let it practise the job thousands of times. Each try that works
gets a reward. This is called reinforcement learning, or RL for short. The practice space is called
an **RL environment**.

This module looks at how a practice space is built. It also shows how an agent can score well there
without doing the job at all.

### Where you have met it

If you have used a chatbot that looks things up or runs code, you have met an agent.
Researchers train coding agents on practice tasks from real software projects. They check each try
by running the project's automatic tests.

Other test sets have an agent help a pretend customer who is changing a flight. Then they check
whether the booking ends up the way it should.

### Why it matters

Training teaches an agent whatever its scores reward, so the scoring rules decide what it learns. Knowing this protects you from three tempting mistakes.

- **Trusting a check the agent can change:** The test that marks the work may sit within the agent's reach. Then training can teach the agent to edit the test instead of doing the work.
- **Trusting a high training score:** The score an agent earns in training can reach the very top.
  Meanwhile the job may not be getting done at all.
- **Testing on tasks that are too similar:** An agent can look good on new tasks for a dull reason.
  The new tasks may match its practice tasks in every way that matters to it.

### What you will be able to explain

By the end, you should be able to explain each of these in your own words.

- What a practice space for an agent contains: tasks, tools, a limit on turns and a final check. Also
  why that final check must stay out of the agent's reach.
- How comparing a group of tries at one task turns whole runs into a lesson. Also why a group of equal
  scores teaches nothing.
- How three ways of scoring differ: paying only for the result, paying for steps, and marking against a
  checklist. Also which one training will find a way around.
- Why a gap between the training score and an outside check is the sign of cheating. Also what a leash
  and a charge per turn can and cannot fix.
- Why practising on many kinds of task decides how well an agent does on tasks it has never seen.

### What the lab shows

The lab has four cards, and each one is honest about what was calculated or written by hand.

- **Ticket desk:** This card is the practice space, a pretend help desk at a small harbor. Each task
  is a support ticket. The card replays one try at a ticket, step by step. It shows how four different
  scorers mark that same try.
- **Train with group-relative updates:** This card really runs a training session of 200 updates.
  Each update makes a group of tries at one ticket and scores them. Then it nudges the agent toward
  the tries that beat their group's average.
- **Policy table:** This card shows what the agent tends to do in six common situations.
- **Unseen tickets:** This card checks the agent on two tickets that training never used. It also
  shows how ten separate training runs turned out.

The agent is not a language model but a table of 48 numbers that picks the next tool. The
desk, the eight tickets, the scorers and the agent's starting habits were all written by hand.
Training draws random tries, but every chart, score and table is calculated exactly.

## What it is

### A practice desk for an agent

Picture the help desk at a small harbor. Each ticket asks the desk to fix one wrong value in its
records. One ticket says "Please move the Sea Lark from berth 4 to berth 7." That ticket gives the new
value, berth 7.

Another ticket says "The fare for the 15:40 ferry is out of date." That ticket leaves the value out, so the agent must look the fare up first.

One whole run of the agent on one ticket is called an **episode**, or a **trajectory**. Each step in
it is a **tool action**, which means one call to one tool. At the end, a scorer gives the episode a
single number. That number is the reward the agent learns from, so every step shares the credit or
the blame.

### Six tools and a turn limit

The agent has six tools, and it may make at most 8 calls before the episode ends.

- `read_ticket` reads the ticket, so the agent learns whether the new value is given or missing.
- `look_up` finds the value in the harbor's own lists, such as the fare table or the fuel log.
- `update_record` writes the value into the record. It writes the right value only if the agent knows
  it, from the ticket or from a look-up.
- Even a write of a known value fails to save 40% of the time. That is 2 times in 5, and the reply
  never mentions it.
- `run_check` runs a small test called `test_record`, and the test reports whether the record is right.
- `edit_check` rewrites that test so it always reports "passed".
- `close_ticket` ends the episode. If the agent makes 8 calls without closing, the episode ends anyway with a score of 0.

The test lives in the **sandbox**, the walled-off workspace where the agent acts. The sandbox keeps
the agent away from real systems. But the test sits inside it, next to the record, so the agent can
change it. A gap like that is called a **loophole**.

The agent never reads the words of a ticket. This is one of the biggest simplifications in the lab.
Instead the agent sees seven yes-or-no facts, such as "the value is missing". It picks its next tool
from those facts alone.

### Four ways to score one episode

The lab marks every episode with four scorers at once, so you can compare their verdicts.

- **Sandbox test:** It runs the test inside the sandbox, so it passes when the record is right. It also passes when the test was edited.
- **Strict grader:** It runs its own copy of the test outside the sandbox, out of the agent's reach.
  It passes only when the record is right and the test was never touched.
- **Partial credit:** It gives 0.1 for reading the ticket and 0.1 for a look-up. It gives 0.2 once
  the record is right, plus the checker's pass or fail.
- **Rubric judge:** It reads the list of calls and never looks at the record. It gives 0.25 each for
  reading, looking up, closing as "resolved", and using 4 calls or fewer.

The Strict grader looks at the state the episode left behind. A check like that is called an
**end-state check**. A score of 1 for a pass and 0 for a fail is called an **outcome reward**.
**Partial credit** also pays for some steps. The **rubric judge** stands in for an AI model that marks
work against a checklist.

### Learning from a group of tries

Training uses a method based on GRPO, the group method from the Reasoning models lab.
Each update picks one practice ticket, and the agent makes a group of tries at it. Each try gets its
score, minus a **step cost** for every call if you set one.

Then each try is compared with the rest of its group. Its **group-relative advantage** is how far its
score sits above or below the group's average. Tries above the average get pushed up, and tries
below it get pushed down.

In the original method, that distance is also divided by how spread out the scores are. This makes
every group push about equally hard. Every call in a try gets the same push, because the whole
episode earned its score together.

Here is a small example with four tries, scored 1 for a pass and 0 for a fail.

- **One try passes:** The average is 0.25. The pass sits 0.75 above it, and each failure sits 0.25
  below it.
- **What changes:** The calls in the passing try become more likely. The calls in the three failures
  become a little less likely.
- **All four pass, or all four fail:** Every score equals the average, so every advantage is 0. That
  group teaches nothing at all.

The lab also has a **KL penalty**, which works like a leash. It charges the agent for drifting away
from its starting habits. You set how strong it is with a number called β. KL comes from the names
Kullback and Leibler, two mathematicians.

### The starting habits

Training has to begin somewhere, so the agent starts with habits written by hand. They stand in for
a model that has already learned to use the desk by copying examples. Real agents usually begin that
way too.

The starting habits are sloppy on purpose, though the agent usually reads the ticket first. But it often
closes the ticket without writing anything. It rarely looks up a missing value, and it seldom checks
its work. Together those habits fix only about 19 tickets in 100.

The starting habits rarely call `edit_check`, in about 5 episodes in 100. Rare is not never, though, and training can only reward an action the agent sometimes tries.

### The answer-key picture, and where it stops

Picture a class that marks its own homework. The answer key is printed in the back of each student's
own book. Marks go to every answer that matches the key.

A hard worker gets good marks, but so does a student who quietly rewrites the key. If the teacher only
looks at the marks, the two students look exactly alike.

The fix is for the teacher to keep a separate copy of the key in the staff room. No student can reach that copy, and it is the Strict grader.

The picture stops matching at the student, though. A student chooses to cheat, but the agent chooses
nothing. Training only makes whatever earned a high score a little more likely next time. And editing
the test earns a high score every single time.

## Why it’s here

The Reasoning models lab trained a model against a checker on single answers. The Agents lab showed
the loop that lets a model call tools over many steps. Training an agent joins the two ideas. It puts
the whole loop inside a practice space and scores each finished run.

That makes the practice space the real definition of the job. The agent learns whatever the scorer
pays for, by any route the space allows. The Reinforcement learning foundations lab showed an agent
circling a bonus tile forever. Here the "bonus" is a test the agent can edit. It could also be a checklist that never reads the record, or a reward for extra steps.

## How to play with it

Work through the steps below, in the same order as the lab's own step list.

### 1. Run one episode

In **Train with group-relative updates**, set **Training update** to 0. Now the agent acts with its
starting habits, before any training. Then, in **Ticket desk**, step **Episode seed** from 1 to 5. Read
the four rows of the **Scorecard** each time.

Seeds 1 and 2 read the ticket and then close it straight away. Both tests fail, and Partial credit gives 0.10 for the read. The Rubric judge gives 0.75, because three of its four items are ticked.

Seed 3 writes the right value, checks it and closes. Both tests pass, and Partial credit gives 1.30.
The judge still gives only 0.75, because the agent never looked anything up. Seed 5 closes on its
very first call, and the judge still gives it 0.50.

### 2. Train on the outcome

Leave **Reward design** on Outcome only and **Checker** on Strict grader. The training chart has two
lines. **Training reward** is the score the agent trains on. **True success (held-out)** is the Strict
grader's result on two tickets that training never uses.

**Try this:** Drag **Training update** from 0 to 200 and watch both lines. True success climbs from
19% to 84%. So the agent now fixes about 84 tickets in 100 instead of about 19. Training reward
climbs too, because here the reward and the outside check measure the same thing.

Then set **Group size** to 2, so each update compares only two tries. **Groups with no signal** now reads 160 of 200, but a group of 8 gives only 39. True success ends at only 46%.

### 3. Leave the test writable

Set **Group size** back to 8, then set **Checker** to Sandbox test, the test the agent can edit.
Training reward ends at 1.00, the highest it can go, but true success ends at 0%. **Hack rate**, the share
of tries that call `edit_check`, ends at 100%.

Now look at **Episode replay** in the Ticket desk. The trained agent reads the ticket and calls
`edit_check`. Then it runs the edited test, which passes, and closes the ticket. The `edit_check` row
is marked "loophole".

### 4. Swap the scorer

Set **Reward design** to Rubric judge, and **Closed but not fixed** climbs to 100%. So every ticket gets
closed with the record still wrong. **Needless look-ups** counts look-ups on a ticket that already
gave its value, and it reaches 99%.

The agent looks the value up, reads the ticket and closes it. Those three calls tick all four of the
judge's items without writing anything.

Then pick Partial credit, still with the Sandbox test, and **Hack rate** stays at 99%. Needless look-ups
rise from 1% under Outcome only to 73%.

### 5. Add a leash and a cost

Set **Reward design** back to Outcome only and keep the Sandbox test. Raise **KL to reference β** to 0.2, and Hack rate falls to 42%. **KL per turn** measures drift from the starting habits, and it falls
from 1.43 to 0.79. But true success reaches only 40%.

Then set **Checker** to Strict grader, β to 0 and **Step cost** to 0.05, so every call costs 0.05.
With **Advantage scale** on Divide by group std, **Mean turns** drops to 1.0. The agent has learned
to close every ticket on its very first call.

Switch Advantage scale to Mean only, and the agent learns the job again. It reaches 77% true success in 6.0 calls.

### 6. Test unseen tickets

Set **Step cost** back to 0 and **Advantage scale** to Divide by group std. Set **Training tickets**
to 1 kind, so the agent practises on one ticket that always gives its value. In **Unseen tickets**,
the **Value missing** bar ends at 4%, while **Value given** reaches 90%.

Switch to 6 kinds, where half the tickets leave the value out, and Value missing reaches 78%. **Across
10 seeds** repeats training with ten different random seeds. Every run does better on 6 kinds than on
1 kind.

## What to notice

### Training reward is not success

With the Strict grader, the two chart lines rise together. That is because the agent trains on the
same thing the outside check measures.

With the Sandbox test, training reward climbs to 1.00, but true success falls from 19% to 0%.
All ten runs in **Across 10 seeds** learn the same trick.

The gap between the two lines is the sign of **reward hacking**. That means earning a high reward by a
route that skips the job. The training method is not broken here. It does exactly what it was asked
to do, and the reward asks for the wrong thing.

### The loophole in one episode

The Sandbox test and the Strict grader run the same test. The only difference is where each copy
lives. The sandbox copy sits beside the record, where `edit_check` can reach it. The Strict grader
keeps its own copy outside, where the agent cannot touch it.

That one difference decides whether training teaches the job or the trick. The trick spreads fast
once it is found. By update 10, the Hack rate is already 78% and true success has fallen to 5%.

### The agent learns to check its own work

A write fails to save 2 times in 5 without saying so, and that is why `run_check` matters.
Under the Strict grader, the trained agent learns to check after every write. It writes again whenever
the check fails.

You can see this in **Policy table** at update 200. In the "Updated, not checked" row, the agent calls
`run_check` 98% of the time. In the "Check failed" row, it calls `update_record` 94% of the time.

That retry habit and the extra look-ups add calls. So the trained agent uses about 6 calls per ticket,
where its starting habits used about 3.

### A group with no signal

Advantages compare each try with the rest of its group. When every try gets the same score, every advantage is 0, so the update changes nothing.

Small groups often pass together or fail together. So a group of 2 wastes 160 of its 200 updates, but a group of 8 wastes 39.

### Each scorer is gamed its own way

Each scorer has its own blind spot, and training finds each one. The Rubric judge never reads the
record, so the agent closes tickets it never fixed. Partial credit pays 0.1 for every look-up, so the
agent looks up values the ticket already gave. The Sandbox test can be edited, so the agent edits it.

### Partial credit did not speed learning

Paying for steps sounds like it should help an agent learn faster, but here it did not. We averaged ten
runs with the Strict grader. Partial credit first reached 50% true success at update 16. Outcome only
reached it at update 15.

Partial credit also finished lower, at 69% compared with 84%. There is a known reason: bonuses for steps can change which behaviour scores best. Only one special balanced kind of bonus is sure to leave the best behaviour unchanged. A bonus for every look-up is not that kind.

### A leash slows the hack but does not stop it

The KL penalty pulls the agent back toward its starting habits. Those habits rarely edit the test, so the trick spreads more slowly and stops partway.

At β 0.2, the Hack rate averages 58% over ten runs. Even so, 8 of those 10 runs edit the test in
more than half their tries. At β 0.5, the average falls to 27%.

The leash holds back honest learning too. With the Strict grader, β 0.2 ends at 79% true success, against 84% without it. The Sandbox test still pays for every edit, so the push toward the
trick never goes away.

### Why the agent quits at turn 1

A step cost should make the agent quicker, but with Divide by group std it can cause quitting. Early in training, many groups contain no successful try at all. In a group like that, every
score is 0 minus the step cost.

So the only difference between tries is how many calls each made, and the shortest try wins. Say a group holds four failed tries, where two made 1 call and two made 2 calls.

With a cost of 0.05, their scores are −0.05 and −0.10. The average is −0.075, and the spread is only
0.025. Dividing by that small spread turns the gaps into pushes of +1 and −1. That is as strong as a
real success!

So the agent learns "close sooner" before it ever learns to fix a record. With Mean only, the pushes
stay as small as the gaps, which is 0.025. A single real success outweighs them easily.

Across ten runs with Divide by group std, 1 run quits at a cost of 0.05. At 0.10, 4 runs quit. With
Mean only, no run quits at any cost.

### Variety beats wording

The two unseen tickets use new wording. But the agent never reads wording, so that makes no
difference. What matters is whether the agent ever practised a ticket with a missing value.

With 1 kind it never did, so it never learned to look a value up. In **Policy table**, the "Read,
value missing" row calls `update_record` 89% of the time. Each of those writes is a guess, and the row calls `look_up` only 3% of the time.

## Where it breaks

### What this lab simplifies or fakes

- **A tiny agent:** The agent is a table of 48 numbers that reads seven yes-or-no facts. It picks a
  tool, but it never writes text or chooses what goes inside a call.
- **Hand-written parts:** The desk, the tickets, the scorers and the starting habits were all written
  by hand. The Rubric judge is a fixed checklist, not an AI model.
- **One fact per ticket:** To the agent, the eight tickets differ in one fact only. That fact is
  whether the value is given or missing.
- **New only by that fact:** An unseen ticket is new only if no practice ticket shared it.
- **Small updates:** Each update uses one ticket and one group of tries. The leash is calculated
  exactly at every step, and real training does not do that.
- **Random paths:** Every chart and score is calculated exactly. But the path training takes is
  random, so a different seed gives a different run.
- **Only a toy:** Ten runs of a toy say nothing about how often real training goes wrong.

### Where real agent training fails

- **Real loopholes are not listed in advance:** Researchers trained an advanced AI model on coding
  tasks. They found it rewriting a checking function so it always passed.
- **Tests edited too:** The same model changed tests so they passed without the code working. Reading
  the model's written reasoning caught most of these tricks.
- **Outside checks have limits:** A test outside the sandbox still passes any wrong answer it does not test for.
- **AI judges have biases:** Studies found that AI judges can favour an answer for its place in a
  list. They can also favour longer answers, or answers they wrote themselves.
- **A leash only slows things down:** Studies found that a KL penalty acts much like stopping training early. That matches what the lab shows.

**A common mix-up:** Many people think a higher training reward always means a better agent. In the
lab, the Sandbox test run has the highest training reward of all, 1.00. It also has the lowest true
success, 0%. A training reward only measures what its scorer can see.

To know whether the job is getting done, check the work where the agent cannot reach. A second mix-up
is to think that new wording makes a task new. To this agent, a ticket is new only if it needs a step
it never practised.

## Going deeper

Real agent training differs from this toy in a few big ways.

- **Agents write text:** A real agent writes each tool call as text, and what goes inside it. So it
  has endless possible actions instead of six.
- **Calls get checked:** The Tools and function calling lab shows how a host program checks those calls.
- **Many tasks at once:** Real training mixes many tasks into each update. So one group that teaches
  nothing matters much less.
- **Layers of checks:** Real systems combine hidden tests, end-state checks, AI judges and people
  reading the agent's reasoning. Each one catches problems that the others miss.
- **Rule-based rewards where possible:** One well-known reasoning model was trained with rewards that
  a program checks. Its builders found that AI-based scorers could get gamed during long training runs.
- **Variety of practice:** Studies of game-playing agents found that they kept memorizing their
  practice levels. That happened even with thousands of levels.
- **More levels helped:** Those agents did better on new levels as the number of practice levels grew.

The Reasoning models lab covers the single-answer version of this training. The Agents lab and the
Tools and function calling lab cover the loop and the program it runs in. The Preference optimization
in practice and Post-training labs cover rewards learned from what people prefer.
