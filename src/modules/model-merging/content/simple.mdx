## The big picture

Picture a model, a computer program that learns from example text so it can guess what comes next. Say it has already learned from one kind of text, such as a few lines about the weather. Now picture two copies of it. One copy practises on recipe steps, and the other practises on proverbs. Proverbs are short sayings such as “a stitch in time saves nine”.

Training a model a little further like this is called **fine-tuning**, and each copy is called a fine-tune. Each fine-tune gets better at its own new job. But what you really want is one model that can handle both jobs at once.

This module is about **model merging**, a way to build that one model with arithmetic instead of more training. You work out what each round of extra training changed inside the model. Then you combine those two sets of changes and add the result back onto the original. The whole merge takes seconds, and it needs no training text at all.

### Where you have met it

Large language models are the kind of program behind a chatbot. People often adapt one to a new job by training it a little further on new text. Each adaptation leaves behind its own full set of numbers. People have built tools to combine several of those sets into one. One of them, mergekit, is described by its makers as “a toolkit for merging pre-trained language models”.

The *LoRA & adapters* lab showed a cheaper way to adapt a model. It stores each new job as a small add-on file called an adapter. You can merge an adapter’s changes with exactly the same arithmetic. That is why software built for adapters offers the same merge methods you will try here.

### Why it matters

Without merging, there are two ordinary ways to get several skills out of one model, and both cost something. You can keep a separate model for every skill and switch between them. Or you can gather all the training text and train again on all of it. Merging is a third route, and it reuses the training you have already done instead of repeating it.

The catch is that a merge is a guess. Nothing checks the combined numbers against either job while the arithmetic runs. A skill can quietly get weaker. The only way to find out is to test the merged model on every job. This lab runs those tests for you, and it shows where each merge loses ground and why.

### What you will be able to explain

By the end of this lesson, you should be able to explain these three ideas in your own words:

- Why a merge is arithmetic on the changes that two fine-tunes made to one shared starting model. It is not a second round of training.
- How to tell apart two reasons a merge can score worse. In one, each job’s own changes get watered down. In the other, one job’s changes truly get in the other’s way.
- What three methods, called TIES, DARE and SLERP, each do differently from a plain average of the changes.

### What the lab lets you do

Every number in this lab comes from real training inside the app. The model is very small and guesses the next letter of a text. The texts and training runs are fixed. The lab measures every score on the same text the models trained on. The only random part you can redraw is DARE’s, with **New random mask**.

The lab has three cards, and each one shows a different part of the story:

- **Task vectors** draws the two lists of changes as two coloured maps. It also counts where they agree and where they pull in opposite directions.
- **Merge recipe** lets you pick one of five merge methods. It prints the exact arithmetic with real numbers and draws ten of the changes before and after the merge.
- **Two task losses** scores every merge on both jobs at once. It compares each one with the models trained for one job alone. It also splits any lost skill into two causes.

There is one surprise to watch for. The plainest merge, an even average, is worse at recipes than the recipe model. It is also worse at proverbs than the proverb model. Yet in that same merge, each job’s changes actually helped the other job. Working out how both can be true is the heart of this lesson.

## What it is

### The model: a table of 900 scores

The model in this lab reads one character and guesses which character comes next. Its alphabet has 30 characters. Those are a space, the 26 letters, a full stop and two bracket symbols. The two bracket symbols never appear in the texts.

Everything the model has learned sits in one table. It has a row for each character the model might read. It has a column for each character that might come next. Each cell holds a score, and a higher score makes that pairing more likely. Take the cell in row `h` and column `e`. It grows high when the training text keeps putting an `e` after an `h`, as in “the”.

To make a guess, the model turns one row of scores into chances that add up to 100%. Bigger scores get bigger chances, and the raw scores before that step are called **logits**. The lab uses that word on its maps.

The lab names each cell by its pair of characters. So `h→a` means the score for an `a` coming right after an `h`. With 30 rows and 30 columns, the table holds 900 numbers, called **weights**. The lab’s formulas write the whole set as θ, the Greek letter theta.

### The starting model

The starting model is called the **base**. It was trained on Harbor weather notes, which are eight short lines about fog, wind, rain and boats. It went through that text 48 times, and one full pass over the training text is called an **epoch**.

The lab measures how well a model fits a text with a **loss**. The loss is the average of how surprised the model is by each real next character. If the model gave the real next character a high chance, say 90%, it is barely surprised. If it gave that character only 1%, it is very surprised, and the loss goes up.

A lower loss is better. The lab measures surprise in units called **nats**, so it reports each loss in nats per character.

You do not need to know how a nat is defined. One fact is enough to read the numbers. A model that spreads its guesses evenly over all 30 characters would score about 3.4. So anything below 3.4 means the model has picked up real patterns from its training text. The base’s loss is 2.553 on Recipe steps and 2.684 on Proverbs, two texts it never trained on. So it already beats even guessing on both.

### Fine-tuning leaves a list of changes

Next, the lab trains two copies of the base further for 20 epochs each. One learns Recipe steps and the other learns Proverbs. Recipe steps is eight lines such as “stir the onions until they turn soft and sweet”. Proverbs is ten sayings such as “the early bird gets the worm”.

This is the fine-tuning from the big picture. The lab calls the two fine-tunes the **specialists**, since each one trains for a single job. After training, the recipe specialist’s loss on recipes is 2.123, a clear drop from the base’s 2.553. In the same way, the proverb specialist’s loss on proverbs is 2.169, down from the base’s 2.684.

Now compare each fine-tune with the base, cell by cell. In each of the 900 cells, subtract the base’s score from the fine-tune’s score. This uses the scores in the table, not the losses you just read. You get a list of 900 changes, one for each weight. Each change tells you how far training moved that score up or down.

A list of numbers like this is called a **vector**. So this list of changes is the fine-tune’s **task vector**. The **Task vectors** card writes it as `τ = θ_tuned − θ_base`. Here τ, said “tau”, stands for the task vector. The other two symbols stand for the fine-tune’s weights and the base’s weights. So the formula reads “tuned minus base”.

Here is one real cell, `h→a`. In the proverbs, an `a` follows an `h` five times, in words such as “what”, “has” and “than”. In the recipe steps that never happens.

So the proverb fine-tune raised the `h→a` score by 1.18, and the recipe fine-tune lowered it by 0.89. The two task vectors hold +1.18 and −0.89 in that one spot. This kind of disagreement is what the lesson keeps coming back to.

### Reading the two maps

The card draws each task vector as a 30 by 30 map, `τ recipes` and `τ proverbs`. Rows are the previous character, and columns are the next one. A blue cell means the fine-tune raised that logit, and a red cell means it lowered it. Grey means the cell did not change, or changed too little to show.

The deeper the colour, the bigger the change. Both maps share one colour scale, so you can compare them fairly. A few rows stay grey on both maps. Those are the rows for `j`, `q`, `x`, `z` and the two bracket symbols. None of those characters appears in either text, so training never gives their rows any reason to move.

Every other row changes in all 30 cells, because training on a row nudges every score in it. It raises the real next characters and lowers the rest. Both texts use the same set of 24 characters, so both fine-tunes change the same 24 rows. With 30 cells in each row, that makes 720 changed cells out of the table’s 900.

### A picture to hold on to: two sound engineers

Picture a sound desk at a concert, with a long row of sliders. Each slider sets how loud one microphone or instrument is. Say this desk has 900 sliders, and think of their starting positions as the base model.

Two sound engineers each get an exact copy of that desk. Each one adjusts their copy for a different song. When they finish, each engineer writes down how far they moved every slider. A note might say “slider 3, up a lot” or “slider 7, down a little”. Each engineer’s list of moves is a task vector. It records the change from the starting desk, not the final positions.

A merge takes a fresh copy of the original desk. It applies some mix of the two lists of moves. The simplest mix gives each slider half of the first engineer’s move and half of the second’s.

Where both engineers moved a slider the same way, the merge moves it that way too. Where one moved it up and the other moved it down, the two moves partly cancel each other out. That clash is called a **sign conflict**, because one change is plus and the other is minus.

The picture stops matching in two places. The first is about labels, because on a real desk every slider has a label, such as “drums”. So you can read what each move does. In this tiny model you can read each number too. Each one is the score for one pair of characters. In a big model, though, a single number usually has no meaning that anyone could name.

The second difference is that a slider on a desk sets its own sound and nothing else. Here the 30 scores in a row share out 100% of the chances between them. So raising one score lowers the chances of every other character in that row.

### Why both must start from the same base

The two lists of moves only make sense together because both engineers started from the same desk. That requirement is called the **shared base**. It means every model in a merge must have been fine-tuned from the same starting model. Then any one cell, say cell number 417, means the same thing in both task vectors. So adding them cell by cell adds like to like.

Now picture two desks that were wired by different people. Slider 417 controls the drums on one desk and the singer on the other. Adding the two engineers’ moves slider by slider would then mix up sounds that are unrelated.

Bigger models have the same problem. Between their input and their output they have inner parts called **hidden units**. Each hidden unit comes to respond to some pattern during training. Nothing decides ahead of time which unit ends up with which pattern.

Before any training, a model’s numbers start at random values, and training then adjusts them step by step. Two models with different random starts can end up with their hidden units in a different order. They can still do the same job. Averaging them number by number would then mix unrelated units, like the two desks wired by different people.

Fine-tunes of one model avoid this problem. Both inherit the same wiring from their base and usually move only a short way from it. Imagine sliding from one fine-tune’s weights to the other’s, with every cell moving at the same steady pace.

Say one cell holds 1.0 in the first fine-tune and 3.0 in the second, which are made-up numbers. A quarter of the way along, that cell holds 1.5. Halfway it holds 2.0, and three quarters of the way it holds 2.5. Every other cell slides from its first value to its second in the same way, at the same time.

Now check the loss at each stop along the way. For fine-tunes of one model, the loss usually stays low at every stop. There is no hump in the middle where the model suddenly gets much worse. That property is called **linear mode connectivity**. It is why averaging fine-tunes of one model works at all. Two models trained from different random starts usually do not have it, so somewhere between them the loss climbs.

### Five ways to combine the lists

The **Merge recipe** card offers five methods in its **Merge method** control. All five start from the same two task vectors, and all five end the same way. They add the combined list onto the base, and the result is the model you would actually use.

The lab calls that result **Served weights**. It prints the formula for it with the current numbers filled in. A small line above the card’s title says “no gradient step”. A gradient step means one small training update, so merging trains nothing at all.

#### Linear blend

The `Linear blend` method takes a weighted average of the two fine-tunes. That is an average where each one can count for a different share. This is called **weight averaging**. The **Blend t** slider sets the proverbs’ share, so at 30% it reads “70% recipes · 30% proverbs”.

At 50% each list counts for exactly half. The formula reads `θ = θ_base + 0.50·τ_recipes + 0.50·τ_proverbs`. In words, that means “the base, plus half of the recipe list, plus half of the proverb list”.

For the `h→a` cell, half of −0.89 is about −0.45, and half of +1.18 is about +0.59. Added together, they move that cell up by only about +0.14. So the average gives neither task much of what it wanted.

Both fine-tunes share the base. So averaging their task vectors gives exactly the same model as averaging the fine-tunes’ own weights. A saved copy of a model’s weights is called a **checkpoint**. That is the word the lab uses when its formula note points this out. Here is why, using a made-up base score of 2.00 for the `h→a` cell:

- The recipe fine-tune lowered that score by 0.89, so it holds 1.11 in the cell.
- The proverb fine-tune raised that score by 1.18, so it holds 3.18 in the cell.
- The average of those two scores is 2.145, which equals the base’s 2.00 plus 0.145. Adding half of each change to the base gives the same result.

#### Task arithmetic

The `Task arithmetic` method adds both lists at full strength and then scales the total by one number. That number is written λ, the Greek letter lambda. The **Scale λ** slider sets it from 0 to 1.50. Adding task vectors to a base like this is called **task arithmetic**.

At 1.00 the formula reads `θ = θ_base + 1.00·(τ_recipes + τ_proverbs)`. So the `h→a` cell moves by −0.89 + 1.18, which is +0.29. At a **Scale λ** of 0.5 it gives exactly the same model as the 50/50 average. That is because half of the total equals half of each list.

#### TIES

The `TIES` method is short for **TIES-Merging**. The name comes from its three steps of trim, elect sign and merge:

1. **Trim:** Keep only the biggest changes in each list. The **Keep top** slider sets the share, and every other change becomes zero. Size alone counts here, so −0.89 is a bigger change than +0.5.
2. **Elect:** For each cell, add up the kept changes from both lists. Whichever sign has the larger total wins that cell’s vote.
3. **Merge:** Average only the kept changes that agree with the winning sign. Then scale the result by λ, the same as in task arithmetic.

In sound-desk terms, TIES checks which way each slider got the bigger total push. Then it uses only the moves that went that way.

Take the `h→a` cell again. Both changes are big enough to survive a trim that keeps the top 20% of each list. Their total is +0.29, so plus wins the vote. The average leaves out the recipe list’s minus change, so only the proverb change is left. So with **Scale λ** at 1.00, the merged cell gets the full +1.18 instead of the average’s +0.14.

Where both lists agree and both changes survive the trim, TIES averages them, much as the plain blend does. Beyond that, TIES differs from the plain blend in three ways:

- The trim throws away most of each list. With **Keep top** at 20%, 678 of the 900 merged cells end up at zero.
- Some cells keep only one list’s change after the trim. That change goes in at full strength instead of half. The lab has 84 cells like that.
- In a conflict cell where both changes survive, TIES drops the losing side. It does not let the loser cancel the winner, as `h→a` showed.

Those full-strength cells help explain a result you will see in the lab. TIES with **Scale λ** at 1.00 lands close to plain task arithmetic at the same setting.

#### DARE

The `DARE` method stands for Drop And REscale. It makes a random draw for every change in each list. It throws away each change, meaning it sets it to zero, with a chance of p. You set p with the **Drop rate p** slider. Then it multiplies the survivors by `1 / (1 − p)` to make up for the missing ones.

At p = 0.5, each change has a 50% chance of being dropped. The multiplier is 1 divided by 0.5, which is 2. So every kept change doubles, and the slider reads `50% dropped · ×2.00`. After that, DARE adds the two thinned lists together and scales them by λ, as task arithmetic does.

To see why doubling makes up for the losses on average, picture one change of +0.6, a made-up size. Half the time it drops to zero, and half the time it doubles to +1.2. So over many draws it averages out to the original +0.6.

In any single merge, though, that change is either zero or +1.2, and never the +0.6 it started as. The random choice of which changes to drop is called a **mask**. The **New random mask** button draws a fresh one each time you press it.

#### SLERP

The `SLERP` method stands for spherical linear interpolation. It blends along a curve instead of a straight line, so that the blend does not shrink. To see what shrinking means here, you first need to measure the length of a list of numbers.

Take a list of two numbers, 3 and 4. Draw it as an arrow on graph paper that goes 3 squares across and 4 squares up. Its length is the square root of 3² + 4², which is the square root of 25. So the arrow is 5 squares long. This is the same rule you would use for the long side of a right-angled triangle.

The same rule works for 900 numbers. Square each one, add up all the squares, and take the square root of the total. You cannot draw an arrow that needs 900 numbers to describe it. But its length, and the angle between two such arrows, still work exactly as they do on paper.

The lab prints each task vector’s length under its map as `‖τ‖`. The double bars mean “length of”, and both lengths are about 10. The badge on **Task vectors** reads cosine 0.34. The **cosine** is a score for how closely two arrows point the same way.

A cosine of 1 means the same direction, 0 means a right angle, and −1 means opposite directions. So 0.34 means the two task vectors point partly the same way. Their angle is 69.9°, a little less than a right angle. The cosine on the badge and that angle are the same fact written in two different ways.

Now picture two friends who start at the same lamp post. Each walks a little over 10 steps, in directions about 70° apart. Stand halfway along the straight line between where they stop. You are only about 8.5 steps from the lamp post. Cutting across the corner brings you back toward the start, and that is how an average shrinks.

Now walk around the lamp post instead, on a curve that keeps your distance. You stay a little over 10 steps away the whole time. A plain average takes the straight line between the two arrows, while SLERP takes the curve.

In the lab, the halfway point of the plain average has a length of only 8.46. That is shorter than either task vector. SLERP’s halfway point has a length of 10.32. You can read both numbers on the `‖τ_merged‖` badge of **Merge recipe**.

At the halfway point, SLERP points in exactly the same direction as the average. The only difference is that its arrow is longer. You can check this with the formula the lab prints, which uses sin, the sine key on a calculator.

At **Blend t** 50%, the formula reads `θ = θ_base + (sin(0.50Ω)·τ_recipes + sin(0.50Ω)·τ_proverbs) / sin Ω`. Here Ω, the Greek letter omega, stands for the angle between the two lists. That angle is 69.9°, so half of it is 34.95°.

The formula multiplies each list by sin 34.95°, which a calculator gives as about 0.57. It then divides the total by sin 69.9°, which is about 0.94. Since 0.57 divided by 0.94 is about 0.61, SLERP takes about 0.61 of each list.

The plain average takes only 0.50 of each list, and that bigger share is what keeps SLERP’s arrow long. So at the halfway point, SLERP gives the same model as `Task arithmetic` with **Scale λ** at about 0.61. The curve does nothing more than set that bigger share. SLERP can only combine two lists at a time, so it cannot merge three models in one go.

## Why it’s here

As the big picture said, merging gives you one fixed model with both skills. It starts from two fine-tunes you already have. It works even when you no longer have the text to train again.

The trouble is that nothing tunes the merged numbers for either job. So you have to measure whether both skills survive the arithmetic. Measuring has a trap in it, though. A merged model can score worse than a specialist for two quite different reasons.

The first reason is **shrinking**. It happens when a method uses less than all of each job’s own list. The 50/50 average, for example, uses only half of the recipe list. So the recipe skill gets watered down even if the proverbs did nothing.

The second reason is **interference**. It is the harm one job’s list does to the other job when both lists are added together. That is the real clash between the two skills. It is a separate thing from shrinking, even though both make the score worse.

### The water test

Picture a friend who makes a smoothie with half a cup of strawberries and half a cup of banana. Her usual smoothie has a full cup of strawberries. She complains that it tastes less of strawberry, and she blames the banana for spoiling it.

Before she blames the banana, she can make one more smoothie. This one has half a cup of strawberries and half a cup of water in place of the banana. The water version shows how much flavour she lost by halving the strawberries. Comparing it with the banana version shows what the banana really did.

The lab runs that same test on every merge. To measure interference on recipes, it reruns the merge with the proverb list set to zeros. That list of zeros plays the part of the water. The difference between the two scores is the interference. The picture stops matching in one way: the water smoothie is a real drink she could pour. The lab’s water version is only a check it works out. Nobody would ever use it as a model.

Here is the test with real numbers for the 50/50 average, scored on the recipe text:

1. The recipe specialist, which uses the whole recipe list, scores 2.123 on recipes.
2. Half the recipe list on its own, with zeros in place of the proverbs, scores 2.294. That is 0.171 worse, and all of that comes from shrinking.
3. Half the recipe list plus half the proverb list scores 2.257. That is 0.037 *better* than the water version’s 2.294. So the interference is −0.037, and the minus sign means the proverb list helped the recipes.

On **Two task losses**, the **Gap** column shows the total change from the specialist. That is 2.257 minus 2.123, or +0.134. The **Interference** column shows the part caused by the other list. Whatever is left of the gap is the cost of shrinking.

The two parts add up to the gap, since 0.171 of shrinking plus −0.037 of interference gives 0.134. Because the proverbs helped a little, the total gap is smaller than the shrinking on its own.

Then drag **Recipe epochs** down to 0. The slider changes to read `untrained · τ = 0`, and the recipe map turns grey.

Every merge now uses the proverb list alone. An untrained fine-tune has a task vector made entirely of zeros. The one exception is SLERP. It needs two non-zero lists to measure an angle, so its row falls back to the base model’s losses. Set the slider back to 20 before you go on, so the numbers match the rest of this lesson.

Then read the two **Interference** columns, which show −0.037 and −0.055. Notice that both are negative. The note under the table says why: adding each list helped the other task rather than hurting it.

## What to notice

### Shrinking, not clashing, explains the average

- The average’s gap is mostly shrinking. The recipe list at half strength, alone, scores 2.294, and adding half the proverb list *improves* that to 2.257.
- Both texts are ordinary English, so the two lists point partly the same way. That is what the positive cosine of 0.34 tells you.
- The proverbs help here because the recipe list is only at half strength. The recipe model still has room to improve. Half the proverb list supplies some of that missing push.
- At full strength the recipe list has already done its job. The same overlapping push then overshoots, and the interference turns positive, as the next section shows.
- The cosine is 0.34 in both cases. So the cosine alone cannot tell you whether the other list will help or hurt. How strongly each list is added matters just as much.
- About 87% of the 720 shared cells agree in sign. So two lists can overlap almost everywhere without being in conflict.

### Full strength is where they collide

- **Task arithmetic** at full strength is where the lists collide. Against the same merge without the other list, it costs recipes +0.156 and proverbs +0.089.
- In that row the **Gap** and **Interference** numbers match. With the proverb list removed, the merge is exactly the recipe specialist. So the whole gap comes from the other list, and none comes from shrinking.
- **Scale λ** has a sweet spot. Both losses fall until λ is about 0.7 to 0.8, and then both rise as the dashed path bends back.
- At λ = 0.8, the losses are 2.218 on recipes and 2.241 on proverbs. That beats the 50/50 average on both jobs.
- Below the sweet spot each list is too weak, so turning λ up repairs the shrinking. Above it, the interference grows faster than the repair.

### TIES picks a winner in each conflict

- TIES changes the conflict cells most. In `h→a`, recipes wrote −0.89 and proverbs wrote +1.18, and TIES keeps +1.18 where the average keeps +0.14.
- At **Keep top** 20%, only 38 of the 96 conflicts survive the trim on both sides. So only those 38 need a vote.
- In the other 58, the trim removed at least one side first. So nothing was left on that side to vote with.
- With 20% kept, TIES lands at 2.273 on recipes and 2.280 on proverbs. That is close to plain task arithmetic in this lab.

### DARE breaks this model

- At p = 0, DARE drops nothing and multiplies by 1. So it gives exactly the same numbers as `Task arithmetic` at the same **Scale λ**.
- At p = 0.5, with the starting mask, DARE scores 2.762 on recipes and 2.602 on proverbs. That is worse than every other method here.
- At p = 0.9, DARE drops nine in ten changes and multiplies each kept change by 10. The losses climb to nearly 6.
- Those losses are 5.967 and 5.661. That is far worse than guessing evenly over every character, which scores about 3.4.
- The multiplying keeps each change right on average but not in any single draw. This tiny model also has no spare copies of its changes to fall back on.
- Losing changes alone would only drift the model back toward the base, with losses close to the base’s own. Going far past even guessing comes from the other half of the rule.
- DARE multiplies each surviving change by 10. So those scores land ten times too far, and the model becomes confidently wrong.
- Each press of **New random mask** moves the DARE point. The lab throws away a different set of changes each time.

### SLERP keeps its length

- SLERP at 50% scores 2.226 on recipes and 2.284 on proverbs, which beats the plain average on both jobs.
- The two lists are 69.9° apart. The straight-line halfway point is only 8.46 long, while the curve’s halfway point is 10.32 long.
- Both halfway points face the same direction. So keeping more of each list’s strength is what makes SLERP the better blend here.
- SLERP at 50% is the same model as `Task arithmetic` at **Scale λ** about 0.61. The slider moves in steps of 0.05. At 0.60 the losses come out at 2.229 and 2.287, almost the same.
- The `Task arithmetic` method at 0.80 does better still, so the curve is not special in itself.

### LoRA lists clash far more

- With `LoRA rank 4`, **Sign conflicts** reads 331 (46%), out of the same 720 shared cells. So nearly half the shared cells are pushed in opposite directions.
- That is far more than the roughly 1 in 8 for full fine-tunes. The cosine also drops to 0.19, so the two LoRA lists point in less similar directions.
- At the 50/50 average the LoRA interference stays near zero, while each list is only at half strength.
- The clash shows up once both lists are added whole. At **Scale λ** 1.00, `Task arithmetic` gives interference of about +0.51 and +0.38, against +0.156 and +0.089 for full fine-tunes.

### One file has a price

No merge reaches the `two separate models` cross. That leftover gap is the price of serving one model instead of keeping two.

## Where it breaks

### What this lab simplifies

The app computes every task vector, merge and loss live from real fine-tunes. It records nothing in advance and makes nothing up. The limits come from how small and narrow the experiment is. Each one is worth keeping in mind.

There are only two tasks, and each fine-tune runs once. It uses one **seed**, which is the starting number for its random choices. A different seed could give somewhat different lists, and the model is also tiny, with only 900 weights. Its texts hold only eight recipe lines and ten proverbs.

This lab trains its own base for 48 epochs. The *Fine-tuning & transfer* and *LoRA & adapters* labs use a 60-epoch Harbor model instead. That is why the loss on recipes here is 2.553 rather than the 2.556 you may remember. The difference is only 0.003. That is far smaller than the gaps between a merge and a specialist that this lesson studies. But no lab tests whether it matters.

The lab also scores each merge on the very sentences the fine-tunes trained on. So nothing is held back for a fair test. Picture a student who practises with the exact questions that will be on the exam. A high mark shows only that they learned those questions. In the same way, these scores say which merge fits these sentences. They do not say which would do best on new recipes or proverbs.

The strip shows only 10 of the 900 cells, picked because they are the biggest conflicts and agreements. The other 890 cells still count in every loss.

The lab applies SLERP to the task vectors rather than to whole models. That lets you see the curve clearly. Real tools such as mergekit apply SLERP to whole models instead. Think of each whole model as one long arrow. It is the long base arrow plus a short arrow of changes. Two such arrows almost overlap, so there is hardly any corner to cut. In real use, SLERP on two fine-tunes of one base gives nearly the same result as a plain blend.

This model is a single table with no hidden units. So it cannot show what goes wrong when two models lack a shared base. Every task vector in the lab starts from the same base on purpose. So you only meet that failure in this lesson’s words.

The lab also tilts against TIES and DARE. Both were built for huge models whose changes are small and highly repetitive. In such models most changes can be trimmed or dropped at little cost. Here every one of the 900 numbers matters.

Picture a school play run by a crew of 900. Each person has a different job that nobody else knows how to do. Send half the crew home at random and ask the rest to work twice as hard. The total effort might stay the same. Yet if the one person who knew the lights went home, nobody could work them.

Now send nine in ten home, as DARE does at p = 0.9. Ask the rest to work ten times as hard. That is worse than the missing jobs, because each person who stays now overdoes their own job. The sound person turns the music up far too loud. That is what DARE does to this lab’s tiny model.

A huge model is more like a crew where many people can cover each job. That is the setting DARE was built for.

DARE also uses a single random mask for each setting. The lab never averages its results over many masks. **New random mask** shows you how far one fresh draw can move the result. That is the only spread you get to see.

The LoRA maps carry one extra quirk. Adding the same amount to every score in a row changes no guess at all. Say every score in the `h` row went up by 1. The gaps between them would stay the same, so the chances for the next character would not change.

The model only cares how the scores in a row compare with each other. Full fine-tunes never add a shift like that, but LoRA adapters do. So part of what the LoRA maps and cosine show makes no difference to any prediction.

**A common mix-up:** Losing to each specialist at its own job is not proof of interference. Averaging halves each task’s own list. Half a list scores worse even when nothing else is added at all. Only the **Interference** columns measure what the other task really did. They rerun the merge with the other list set to zero.

### Where real merging falls short

Real merges are tuned and judged on held-out tests for every task at once. Held-out tests are built from examples the models never trained on. The scale λ is tuned on those tests too, and choosing it well matters as much as choosing the method.

Interference grows as you merge more tasks, and also as the tasks become more different from each other. Two tasks that share a lot, like the two English texts here, clash less. Tasks that pull a model in very different directions clash more.

A merged model can keep its test scores while losing behaviour that no single score captures. One example is the way it lays out its answers. It might also lose its habit of refusing requests it should refuse. It might lose its **calibration**, which is how well its confidence matches how often it is right.

No merge comes with a promise. Merging runs no training step, so nothing guarantees that any skill survives until you test it. Licences also travel with the weights, and a licence sets the rules for how a model may be used. So a merged model inherits every rule from every model that went into it.

## Going deeper

### Subtracting a task

Task arithmetic works in reverse too. You can subtract a task vector instead of adding one, written `θ_base − λ·τ`. People have used this to remove a behaviour that a fine-tune taught. One example is writing toxic text, meaning text that is rude or hurtful.

### Adapters are task vectors too

An **adapter** is a small trained update that you store apart from the base. The LoRA add-on from *LoRA & adapters* is one. Its correction, written `(α / r)·B·A` in that lab, is a list of changes to the base’s weights. That makes it a task vector too. So the software built for adapters offers the same merge methods that you have tried in this lab.

The `LoRA rank 4` option uses adapters with a rank of 4 and an alpha of 8. The line of text above the maps says so. So each adapter’s correction is its two small tables multiplied together. Then you double it, since 8 divided by 4 is 2.

### Methods stack

You can also combine the methods. People often use DARE first to thin out the lists, and then merge them with TIES. SLERP takes exactly two models, so merges of many models use the linear, TIES or DARE methods instead.

Tools such as mergekit apply these rules to one block of weights at a time. They sometimes use a different blend for each layer. A layer is one of the stages a big model passes its input through.

### The cosine, worked out

The cosine on the badge comes from a short calculation. You could do it by hand for a small list. Multiply the two lists cell by cell and add up all the products. Then divide the total by the two lengths multiplied together.

Take two short lists, 3 and 4, and 4 and 3. Both are arrows 5 squares long. Multiplying cell by cell gives 12 and 12, which add up to 24. Dividing 24 by 5 times 5, which is 25, gives a cosine of 0.96. So those two arrows point almost the same way.

Lists that rise and fall together give a cosine near 1. Unrelated lists give one near 0, and lists that move in opposite ways give one near −1.

### Other ways to combine skills

*LoRA & adapters* made the kind of lists this lab combines. *Distillation & pruning* takes a different route to a similar goal. It reaches one smaller model with many behaviours by training rather than arithmetic. That costs computer time, but it actually tunes the result for the job.

### Merge, or serve the adapters side by side

Merging is not the only way to get several tasks out of one base. *LoRA & adapters* ends on the other route. That route keeps one copy of the base and many adapters. It picks the right adapter for each request as it arrives.

Serving software called vLLM does this when you start it with the `--enable-lora` option. A research paper called S-LoRA describes serving thousands of adapters at the same time from one shared base.

The two routes trade differently. Serving keeps each task’s adapter exact, but it costs effort in scheduling requests and managing memory. A merge costs nothing extra when the model runs. But, as this lab measures, it can add interference between the tasks. How much depends on the method and the scale.

Serve the adapters separately when tasks must never interfere. Do the same when you need to add and remove adapters while the system is running. Merge them when one fixed model is enough and your held-out tests show that the interference is small.

### Toy versus real

- **Tools:** mergekit, from Arcee AI, describes itself as “a toolkit for merging pre-trained language models”. You describe a merge in a short settings file that names the models and the method. The file uses a format called YAML.
- **Methods:** The mergekit methods include Linear, SLERP, Task Arithmetic, TIES, DARE and DELLA, among others. This lab rebuilds the first five on a table of 900 numbers.
- **Memory:** mergekit works through a model one piece at a time instead of loading it all at once. So a merge can run on a computer’s main processor alone. It can also use a graphics card with as little as 8 GB of its own memory. A gigabyte, or GB, is about a billion bytes, and one byte holds about one letter of text.
- **Testing:** Here a merge is arithmetic on 900 numbers, and the check is two losses. Real merges face held-out tests for every task. On those tests, one score can hold steady while another slips, so every task needs checking.
- **Adapters:** In Hugging Face’s PEFT library, `merge_and_unload()` folds one adapter into its base for good. The mergekit tool can go the other way with `mergekit-extract-lora`. It builds an adapter that comes close to a full fine-tune’s changes.
- **Side by side:** You can also leave several adapters unmerged. Then you serve them side by side, as the section above describes.
