## The big picture

When you solve a hard math problem, you probably do not write the answer straight away. You fill
some scratch paper with working, check each line, and only then copy a final answer into the box.
Some AI models have been trained to do something similar, writing out a long stretch of steps
before they answer, and they are called **reasoning models**. This module looks
at where that habit comes from, what it costs, and what the written steps do and do not prove.

### Where you have met it

If you have ever asked a chatbot to show its working, you have seen one way to get steps out of a
model, which is to ask for them. A reasoning model gets there by a different route, because it was
trained to write long working without being asked. That training uses a program that checks final
answers, such as an answer key for math questions or a set of automatic tests for computer code.

The same ideas turn up in other places too. Smaller models are sometimes trained to copy the long
working of a stronger model. AI agents, which are programs that take actions such as running a
search, spend extra time and computing power on those actions instead of on writing more working.

### Why it matters

A program that checks answers is what lets this training run without a person grading every try,
and understanding how it all works protects you from three tempting mistakes:

- **Reading working as a true record:** long working looks like careful thought, so it is tempting
  to treat it as the real story of how the answer was reached. It is generated text, and some lines can
  be filler or even wrong while the final answer is right.
- **Paying for length that does little:** every extra line costs time and computing power, even
  when it adds nothing to the answer. If training never puts a price on length, the working keeps
  growing even when each extra line makes the answers only a tiny bit better.
- **Trusting the wrong way to pick an answer:** another way to spend extra effort is to make several
  tries and pick one of them. Picking by a vote can leave you right less often than a single try
  would, while a perfect checker never can, and you need to know when each one applies.

### What you will be able to explain

By the end, you should be able to explain each of these in your own words:

- Why a reasoning model is different from a model asked for steps in a prompt, since a prompt
  changes only what the model reads. Training against a checker changes the model itself, so that
  long working becomes its habit.
- How comparing a group of tries against a checker makes the working longer, and why, when nothing
  charges for length, it keeps growing past what the task needs.
- Why extra working, or extra tries, is extra generated text and extra searching, not proof of
  thoughts going on inside the model.
- When taking a vote among several tries helps, and when only a checker can find the right answer.

## What it is

### Working, one piece at a time

A language model writes text one small piece at a time, and each piece, a word or part of a word,
is called a **token**. For every new token it reads everything written so far, picks the next
piece, adds it to the end, and repeats. The steps a model writes before its final answer are called
a **chain of thought**, because each step links to the next like the links of a chain.

Here is the working the lab shows for the question "What is 17 + 28?":

```
1. Add the ones: 7 + 8 = 15, write 5 carry 1.
2. Add the tens: 1 + 2 + 1 = 4.
3. The pair is 45.
```

Each line is ordinary text, written one token at a time like any other sentence, and the final
answer comes only after the working.

### Two ways to get working: ask for it, or train for it

Inside every model is a huge set of adjustable numbers, called **weights**, which training sets and
which decide what the model tends to write. There are two quite different ways to get a model to
write working, and the difference is whether those weights change.

The first way is to ask: you put a couple of worked examples in your message, which is called the
prompt, and the model tends to copy their style. This is in-context prompting, which the ICL &
reasoning lab covers (ICL is short for in-context learning). It leaves every
weight exactly as it was, because only what the model reads has changed.

The second way is to train: after its main training, the model gets extra training, called
post-training, that changes its weights. That makes long working likely even when nobody asks for
it, and a model trained this way is called a **reasoning model**. Its design is the same as any
other language model's, so it still writes one token at a time, and only the training recipe is
different.

### Training against a checker

The recipe is a kind of **reinforcement learning**, which means learning by trial and score: the
model makes tries, and each try gets a score. The weights then shift so that the high-scoring kind of
try becomes more likely next time.

Here the score comes from a program that checks the final answer, which for 17 + 28 means comparing
it with 45. For computer code the program might run small automatic checks, called unit tests, that
confirm the code gives the right outputs. A score that a program can compute like this is called a
**verifiable reward**, and training with it is called **RLVR**, short for reinforcement learning
with verifiable rewards.

Each round of RLVR has three steps, and the lab's training card runs a tiny version of the same
loop:

1. The model writes several tries at the same question, each with its own working.
2. A checker program marks each final answer as a pass or a fail, without looking at the working.
3. The weights are nudged so that the working in the passing tries becomes a little more likely, and
   the working in the failing tries a little less likely.

No person has to grade any try, which makes the method cheap, but the model can only learn what the
checker can tell apart. Since the checker looks only at the final answer, it rewards the working
that comes before a pass, whether every line of it was needed or not.

### Grading on a curve: GRPO

One way to do the nudging, and the one this lab copies, is called **GRPO**, and it never judges a
try on its own. Instead it compares each try with the other tries in its group, much like a test
graded on a curve, where your mark depends on the class average.

Each try's score is turned into an **advantage**, a number that says how much better or worse the
try did than its group's average. Tries above the average get pushed up and tries below it get
pushed down, and the size of each push is scaled by how spread out the scores are. That scaling
makes the pushes come out at about the same size, whether the scores in a group differ a lot or
only a little. Because the group itself is the yardstick, nothing else has to judge what counts as
a good score.

To measure how spread out a group's scores are, take each score's distance from the average and
square it. Then average those squares and take the square root. A try's advantage is its distance
from the average divided by that spread.

Here is a small example with a group of four tries, where a pass scores 1 and a fail scores 0:

- If half the group passes, the average score is 0.5 and every score sits 0.5 away from it, so the
  spread is 0.5. Each passing try gets 0.5 ÷ 0.5 = +1, and each failing try gets −0.5 ÷ 0.5 = −1.
- If only one try passes, the average is 0.25 and the spread works out to about 0.43. The lone pass
  sits 0.75 above the average, so it gets 0.75 ÷ 0.43, or about +1.73. Each of the three failures
  sits 0.25 below, so it gets a small −0.58. A rare success is pushed up hard, because it stands
  out so clearly from the rest of its group.
- If all four pass, or all four fail, every score equals the average, so every advantage is 0 and
  that group teaches nothing at all.

Keep that last case in mind, because the lab's Groups with no signal readout counts exactly those
groups.

### Test-time compute

Everything so far happens during training, while **test-time compute** is the extra work a model
spends later, while it is answering you. It comes in two kinds: a model can write longer working
before its answer, or it can make several separate tries and use some way to pick one. A bigger
version of the second kind, called **search**, judges working that is still half-written and keeps
going only with the most promising tries, which Going deeper describes. Every kind costs more tokens
and more waiting time, but none of them changes the weights, so the model itself is no different
afterward.

### The scratch-paper picture, and where it stops

Picture a student who sits test after test where the teacher marks only the answer box and never
looks at the scratch paper. Every right answer earns a gold star, and the papers that earn stars
tend to be the ones with more working above the answer. Test after test, the student drifts toward
whatever habits came with stars, so their scratch paper slowly fills up, even though nobody ever
marks the working itself. Training against a checker works in a similar way: long working appears
because it is more often followed by a right answer.

The picture stops matching at the student, who can decide to show more work because they understand
why it helps. The model decides nothing, and nobody shows it a method. Training only makes whatever
working came before a pass a little more likely, and long working comes along because it is more
often followed by a pass.

## Why it’s here

Reasoning models deal with two separate problems, one about how a model computes and one about how it
can be trained, and this lab connects them.

### A fixed amount of work per token

To choose each token, the model pushes everything written so far through the same set of weights
once. That is a huge sum, and it grows a little as the text gets longer. But the sum always passes
through the same fixed number of stages, one after another. So the model can chain together only
about the same amount of work for every token, however hard the question is.

Picture being allowed exactly three seconds of thinking before every word you say. Some problems
need a chain of steps where each step uses the result of the one before, and a long chain may not
fit into three seconds. In 17 + 28, for example, you cannot finish the tens until you know whether
adding the ones produced a carry. On a sum this small you would manage. But a model that had to
produce the answer to a long problem in one go would need to squeeze the whole chain into a single
fixed-size calculation.

Writing working changes that, because if you can write a note after each three seconds, you can
carry on from the note. Once the model has written "write 5 carry 1", the carry sits in the text
where the next step can read it. In this way, working
spreads a long chain of steps across many tokens and each token's calculation handles only a small
part. That is the real reason working can help, and it is also why working helps most on problems
where later steps depend on earlier results.

### Building the habit without a human grader

A prompt cannot build the habit of long working into the weights, so you need a training signal.
The Reinforcement learning foundations lab showed a learner improving against a reward. The
hard part is finding a reward, and a checker program fits well because it is cheap to run and hard
to argue with. That means it can score a huge number of tries without anyone having to read them.

This lab joins the two ideas, because the reward is the checker and the learner is something that
writes working. The sampling card adds one more idea, the chance that at least one of several tries
works, which the Evaluation lab also uses.

## What to notice

### Length grows because the checker rewards it

In this toy, every step of the working lands, meaning it comes out right, with a chance of 0.80,
which is 4 times out of 5. The
answer passes when at least k steps land, so with k = 3, any try shorter than 3 steps can never
pass. A try of exactly 3 steps passes only when all three steps land, and 0.8 × 0.8 × 0.8 = 0.512,
so it passes about 51% of the time.

Think of this rule as standing in for "is the final answer right?" The answer comes out right when
enough steps landed, and the checker sees only that pass or fail, never which steps slipped.

Longer tries have spare steps that can cover a slip, which is why the dashed line on the bar chart
climbs fast as the length grows. A try of 4 steps passes about 82% of the time, and a try of 6 steps
passes about 98%. The checker never rewards length directly, but longer tries pass more often, so
they earn more reward and the policy drifts toward them.

### With no price on length, it keeps growing

Once nearly every try passes, you might expect the length to stop growing, but it does not. With
the cost off, nothing pushes back, and each extra step still adds a sliver of pass chance. In the
groups that still contain a failure, that lone failure gets a large negative advantage. It works
like the +1.73 a lone pass got in the four-try example, but it points down, and in a group of 16 it
is even bigger, about −3.87. That failure is usually one of the shorter tries. So each of those groups
pushes the policy longer, and the length keeps creeping up. At update 100, Steps past k still reads
4.1, which means the average try is about four steps longer than the task needs.

This drift is called **overthinking**: working beyond what the answer needs, which adds waiting time
without adding understanding. In this toy the extra steps are not pure waste, since each one still
buys a sliver of pass chance. But that sliver gets smaller with every step, while the time each step
costs stays the same. The length cost below trims away the steps whose sliver is worth less than
their cost.

The Groups with no signal readout shows why training slows down while the length keeps drifting,
because it reads 51 of 100 at the end of the run. In 51 of the 100 updates every try in the group
got the same score, mostly because they all passed, so those groups taught nothing. Only the other
updates, the ones with a rare failure, kept pushing.

Picture a class where long answers are never marked down, and an answer with extra lines is very
slightly less likely to lose a mark. Week by week the answers that keep full marks are the longer
ones, so answers drift longer while marks creep up only a hair. Unlike the students, the model is
not choosing to be careful: longer tries simply passed a little more often, so they became a little
more likely.

### A price trims length, but not down to k

With Length cost on, each step costs 0.05, so a step is worth adding only if it raises the pass
chance by more than 5 percentage points. That is because a pass is worth 1 point, so raising the
pass chance by 5 percentage points earns 0.05 points on average, exactly what the step costs. Adding a fifth step raises the pass chance from about 82%
to 94%, a gain of 12 points, so that step pays for itself. A sixth step raises it only from 94% to
about 98%, a gain of about 4 points, so that step costs more than it earns.

That is why the run with the cost hovers around 5 steps, ending at 5.3 on this seed. That is 2.3
steps past k rather than right at 3, but well short of the 7 you saw without the cost. The spare
steps still protect against a slip, and the cost removes only the steps that no longer pay for
themselves.

### Why a small group collapses

The collapse at Group size 8 comes from grading on a curve when nobody passes. At the start, about 4
in 5 tries are shorter than 3 steps, so they can never pass. A small group often contains no pass at
all, and every group like that pushes the policy shorter, which makes the next pass even less
likely.

When every try fails, the only difference between them is the length cost. Say a group holds four
failed tries, two with 1 step and two with 2 steps. The 1-step tries lose 0.05 each for their cost,
while the 2-step tries lose 0.10 each. So the scores are −0.05 and −0.10, the average is −0.075,
and every score sits 0.025 from it, which makes the spread 0.025. That gap is tiny, but dividing
by a spread of 0.025 blows it up, so the short tries get an advantage of +1 and the long tries get
−1. That is the same
size of push that a pass gets over a fail, so the policy learns "shorter is better" before it has
ever seen a pass.

Picture a quiz where every paper in the class fails, but the teacher still has to grade on a curve.
If the only difference between the papers is how much scratch paper each one used, the shortest
papers get the top marks. Week after week, the class learns to write less and less, and nobody ever
gets close to a right answer.

That is why Group size matters, because a group of 16 is much more likely to catch at least one pass
early on. A single pass is worth far more than any cost difference, so it points the run toward
longer working instead.

### Working helps most where a later step needs an earlier result

On 17 + 28, the first line writes the carry and the second line reads it, so the working acts as
memory. On Sunday hours the steps mostly look facts up. Only the third one leans on the others,
picking the Sunday slot from the two facts the first two steps wrote down.

After the useful steps, the trace shows two kinds of extra text that add tokens without helping the
answer. **Padding** restates or recalls something the answer never uses, and it is harmless filler
that does not pretend to be part of the work. An example is "Note that addition is associative,
which is unused here." That line states a true fact, that it does not matter which pair you add
first when you add three numbers, but this sum never needs it.

An **unfaithful step** does not match the work the answer needs, yet it presents itself as part of
that work. It might use the wrong operation, invent a rule, or drag in a fact as if it mattered. On
17 + 28 it reads "Check 17 × 28 as if the task were a product", which multiplies when the question
asked for addition. That is why an unfaithful step misleads anyone who reads the working as a record
of how the answer was found.

The lab puts a right answer next to the unfaithful step on purpose, to show something real models
do too. A right answer and working that honestly matches it are two separate things, and a model
can produce one without the other.

### A checker needs only one right try

A program or model that checks a candidate answer is called a **verifier**. When it is perfect,
such as an exact answer key or a full set of tests, you can make n tries and keep any try it
accepts. You succeed whenever at least one try is right, and that chance is called
**pass@n**. Keeping the try that the verifier scores best is called **best-of-n**, and with a
perfect verifier it succeeds exactly as often as pass@n says.

The lab's chart labels the formula as `1 − (1 − p)ⁿ`, where p is the chance a single try is right
and n is the number of tries. To work it out with p = 0.40, notice that a single try is wrong 60% of
the time. Two tries are therefore both wrong 0.6 × 0.6 = 0.36 of the time, or 36%. So at least one
of the two is right 1 − 0.36 = 0.64 of the time, which is 64%. With eight tries the chance reaches
98%, and with 16 tries it reaches the 99.97% you saw on Verifier picks.

### A vote follows the most popular answer

A **majority vote** needs no checker at all, because it makes several tries and returns whichever
final answer comes up most often. That works well when the right answer is the single most common
answer, and badly when one particular wrong answer is more common than the right one.

Picture a group chat settling 17 + 28 by poll, where everyone who gets it wrong made the same slip
of forgetting the carry and answered 35. If 40% of the chat answers 45 while the other 60% all
answer 35, the poll picks 35. Adding more people only makes that wrong result more certain, which is
exactly what the Always the same one setting shows. There the vote falls to 21.3% at 16 samples, and
adding more tries never lifts it back up, so by 32 samples it is lower still. It is not 0%, because
with only 16 tries, luck sometimes gives 45 more votes than 35.

Now picture the wrong answers scattered evenly across 35, 44 and 46, which is what Split over 3
means. Each wrong answer then gets only about 20% of the votes, so 45 with its 40% is the most
popular single answer, and more voters help.

The bar chart in the card shows this directly, with one bar for each possible number of right tries
out of n. The height of a bar is the chance of getting that many right tries, and its solid part is
the chance that the vote then picks the right answer. One more thing to check is that at 2 samples,
Majority vote always equals One sample, whatever the other settings are. When the two tries
disagree, the vote is a tie settled by a coin toss, so a second try cannot help a vote. With
p = 0.40, both tries are right 0.4 × 0.4 = 0.16 of the time. They split one right and one wrong
0.48 of the time, and the coin toss wins half of those, which adds 0.24. That totals 0.40, the same
as one try.

## Where it breaks

### What this lab simplifies or fakes

- The learner in Train against a checker is one number, the length the toy most likes to write. The
  policy is a hump of odds over working of 1 to 8 steps, centred on that number, so training slides
  the hump rather than setting each bar separately. It is not a language model, so it learns how
  long to write and never what to write.
- The checker is a rule written by hand, in which every step lands with a fixed chance of 0.80, and
  no real checker works that way.
- There is one question instead of many, and each group of tries is used for one push and then
  thrown away. There is also no reference model and no clipping, two parts of real training that
  Going deeper explains.
- The curves and bars are exact averages for the policy at each update, but its path comes from
  randomly drawn groups, so another seed gives another path.
- The working, the labels and the answers on the Thinking budget and Inspectable trace cards were all
  written by hand, and no model writes them. The order of useful, then padding, then unfaithful is
  set by hand too, while a real model mixes them together.
- The answer prints at every budget, even 0, so the lab cannot show that cutting real working short
  usually costs accuracy on hard problems.
- **Process supervision**, which means grading each step of the working instead of only the final
  answer, is named here but never computed.
- In Sampling and voting, p is a number you choose rather than a measured model, every try is
  independent of the others, and the verifier is perfect.

### Where real reasoning models fail

- The collapse you saw is real, because with a length cost and no passing try in the early groups,
  the cost is the only signal. Scaling by the spread makes that small signal look large. Real
  training softens the problem by mixing many questions into each batch, which is the set of tries
  used for one round of training.
- A checker sees only the final answer, so it cannot tell a needed step from a wasted one. Padding
  and unfaithful steps that end in a right answer get rewarded along with everything else.
- Real tries from one model are not independent, because they tend to repeat the same mistakes. The
  lab's math treats every try as separate, so real extra tries can help less than it suggests.
- Best-of-n with a learned grader, which is a second model trained to score answers, can pick an
  answer that fools the grader instead of one that is right.
- Process supervision can catch a wrong step that happens to reach a right answer, but it can still
  reward a smooth-sounding step that the answer never uses.
- Even working that looks useful and leads to a right answer may not be the real route the model
  took. So working is not a window into how the answer was produced.

**A common mix-up:** people often read a model's numbered steps as a faithful record of how it
reached its answer. The steps are generated tokens, though. Researchers have tried changing or
cutting lines of a model's working and letting it carry on, and sometimes it gives exactly the same
answer. If changing the steps does not change the answer, those steps cannot be the full story of
how the answer was reached. So the steps are not a window into a hidden mind. A second mix-up is to think that
asking for steps in a prompt and training a reasoning model are the same thing. A prompt changes only
what the model reads, while training against a checker changes the model's weights.

## Going deeper

Real RLVR and GRPO add four things that this toy leaves out on purpose, to keep the lab small enough
to follow:

- **A policy over every token:** the push reaches the odds of every token the model writes, so a real
  model learns what to write, not only how long.
- **A penalty for drifting:** a penalty called the **KL penalty** (KL comes from the names of
  Kullback and Leibler, the two mathematicians behind it) works like a leash. It measures how far
  the model's writing has moved from a reference model, the version it started from, and charges for
  the distance. That charge keeps the model from drifting into strange text that games the checker instead of solving the problem.
- **Clipping:** real training reuses each batch of tries for several pushes, and clipping stops the
  model from moving too far from the version that made those tries. That keeps the reuse safe.
- **Many questions per batch:** mixing many questions into each batch averages out the noise, and
  groups whose tries all scored the same matter less. That is because the other questions in the
  batch still give a push.

Published versions of GRPO differ in how they size each push, by dividing by the length of each
answer and by how spread out the group's scores are. Those choices matter, because each one changes how long the
answers grow as training goes on.

On hard problems with many steps, reported accuracy rises when models get a bigger thinking budget,
and it falls when they are forced to stop early. Search goes further than voting, because instead of
only comparing finished answers, it also judges working that is still half-written. A system makes
several tries, scores the unfinished working with a trained model that grades each step, called a
process reward model, and continues only the best.

**Distillation** trains a smaller or faster model to copy the long working of a strong reasoning
model. It is a bit like copying a classmate's homework, because the student model copies the text
of the steps, not a guaranteed method for solving the problem. Unlike copied homework, though, the
student model learns to write similar working on new questions it never saw. What it does not get
is any guarantee that the method behind that working is sound.
