## The big picture

Picture typing a question into a chatbot on a harbor's website: “When does the north dock close on Sunday?” A good answer needs the harbor's timetable, and the language model behind the chatbot has no way to open it on its own. The only thing a language model can do is write text, so it cannot click a link, open a file, press a button or send an email.

Even so, some AI assistants look up fresh information, work out exact sums, save notes or send emails for you, and this module explains how that works. The model writes a short request in a strict format, and a separate, ordinary program does the rest. That program reads the request, checks it, decides whether to allow it, does the job and writes back what happened.

### Where you have met it

The jobs that program is willing to do for the model are called tools. Tools are how a model gets fresh information, does exact arithmetic, or changes something in the world, such as saving a note or sending an email. You may have seen this when a chatbot says it is searching the web, or does a sum with a calculator instead of guessing.

Behind the scenes, the companies that run chat services let programmers describe their tools to the model in a standard format, which you will learn to read in this lesson.

The same idea sits underneath AI agents, which are the subject of the next lab. An agent repeats this request-and-reply round trip many times in a row, so everything you learn here happens again at every step.

### Why it matters

Text written by a model can be messy. A request might be cut off halfway, name a tool that does not exist, leave out an input, or put a number where a word belongs. A program that acted on such text without checking it first would crash or do the wrong thing.

A request can also be perfectly tidy and still be a bad idea. A request to email the harbor's private visitor log to everyone at the harbor can be written without a single mistake. Checking the format cannot catch what is wrong with it, because nothing is wrong with the format. So the program needs its own rules about what it is allowed to do, and some actions need a person to say yes first.

Finally, when something goes wrong, the model has to be able to read about it, because its next request is written from the text that comes back. A clear error message is what lets the whole system try again and fix the mistake.

### What you will be able to explain

By the end of this lesson, you should be able to explain these ideas in your own words:

- how the model's job, writing text that names a tool and its inputs, differs from the program's job of reading, checking, deciding, running the tool and reporting back;
- how a rule sheet for a tool's inputs, called a **JSON Schema**, helps you name six ways a request can be broken, and what comes back for each;
- why a request that passes every check can still need a separate yes or no, and why controlling the model's writing as it goes cannot supply it;
- how a failed request comes back as a message that the next request can use to fix its inputs, and why the fixed request gets checked from the start.

### What the lab lets you see and try

The lab is set at a made-up harbor whose program offers three tools. One looks up when a dock closes, one saves a short note, and one sends an email from the harbor office. You pick a request from a row of buttons or type your own, and four cards show what happens to it:

- **Model output** holds the request as raw text, exactly as a model would write it, and you can edit it.
- **Host pipeline** walks the request through ten numbered stages, from the tool list to the reply, and marks the stage where it stops.
- **Schema check** shows the rule sheet for the tool being asked for, and it lists every rule the request breaks.
- **Transcript** lists the messages in order, which is everything the model would read on its next turn.

No AI model runs in this lab, so the requests were written by hand to show one problem each. Every check after them is real code, though, and those checks run again on whatever text sits in the box, including anything you type. One readout you will meet later, **Grammar blocks it**, is different, because it comes from a simple rule based on which check failed rather than from running anything.

## What it is

### An everyday picture: the office with a slot

Picture a harbor office where the clerk works behind a wall, and the only way to reach the clerk is to push a paper form through a slot. You cannot walk into the back room, open the drawers or use the office phone yourself. All you can do is fill in a form and push it through.

On the other side, the clerk works through the same checklist every time. First the clerk checks that the form is readable at all, and then that it is a kind of form this office actually handles. Next, the clerk checks that every required box has been filled in. Each answer must also be the right kind, with a word where a word belongs and a number where a number belongs.

The clerk also checks that each tick is one of the printed choices, and that nobody has scribbled in an extra box the form does not have. Then the clerk checks the office rules, because some jobs need a manager's signature. Only after all that does the clerk do the job, write what happened on a reply slip and push the slip back through the slot.

If something is wrong, you still get a reply slip, but this one says what went wrong and where, such as “box 2 needs a word, not a number.” You can fill in a fresh form and push it through again, and the clerk checks the new form from the top, as if it were the first one.

In function calling, the model is the person holding the pen, and the program that runs the model is the clerk. The rest of this section turns each part of that picture into the real mechanism, and the end of the section points out where the picture stops matching.

### A model can only write text

A language model produces text one small chunk at a time, and each chunk, called a token, is often a word or a piece of a word. Writing text is the model's whole job, so it has no way to open a website, read a clock or change anything outside itself.

The ordinary program that runs the model is called the **host**, and a chat app is one kind of host. The host gathers the text the model should read, collects what the model writes, and decides what to do with it. Function calling is a set of rules, which programmers call a protocol, that lets the model's text ask its host to do something.

### Tools, functions and arguments

In programming, a **function** is a named job that a program knows how to do, and it usually needs some inputs before it can do it. One function in this lab is called `get_dock_hours`: you give it a dock and a kind of day, and it gives back the closing time. The inputs a function needs are called its **arguments**, so the arguments of `get_dock_hours` are the dock and the day.

A **tool** is a function that the host is willing to run when the model asks for it. The host describes each tool to the model with three things: a name, a sentence saying what the tool does, and a rule sheet for its arguments.

That sentence is called the **tool description**, and it is the part the model reads as ordinary language, so it shapes which tool the model's call names. For `get_dock_hours`, the description says “Closing time for one dock on one kind of day.”

This lab offers three tools, and each one does a different kind of job:

- `get_dock_hours` looks up a closing time in a small table, and because it only reads the table, it changes nothing.
- `add_note` saves a reminder in the host's memory, and the reminder can be up to 60 characters long, where a character means one letter, space or punctuation mark.
- `send_email` sends an email from the harbor office account, with an address and a message of up to 200 characters.

### JSON: a way to write labelled values

The model's request has to be written in a format the host can read without any guessing, and the usual choice is called **JSON**. JSON writes information as labels paired with values, a bit like the boxes on a form, where each box has a printed label and something written in it. Curly brackets wrap a group, each label sits in double quotes with a colon after it, and commas separate one pair from the next.

Here is the request that asks when the north dock closes on Sunday:

```text
{"name": "get_dock_hours", "arguments": {"dock": "north", "day": "sunday"}}
```

Read it from the outside in, starting with the label `name`, which says which tool to use. The label `arguments` holds a smaller group with the inputs, where the dock is `north` and the day is `sunday`. A piece of text like this, which names a tool and fills in its arguments, is called a **function call**.

Two words from JSON show up in the lab's error messages, so they are worth learning now. A value written inside quotes, such as `"north"`, is called a **string**, which means a piece of text. A whole number written without quotes, such as `7`, is called an **integer**, and JSON can also hold `true` and `false`, which work like a yes or a no.

The most important fact about a function call is that it is only a request. Writing it does not run anything, in the same way that filling in a form does not get the job done. Nothing happens until the host reads the text and chooses to act on it.

### The rule sheet: JSON Schema

Every tool comes with a rule sheet that says what its arguments must look like. These rules are written in a standard format called **JSON Schema**, which is itself written in JSON. A schema can say what kind of value each argument must be, which arguments are required and which values are allowed.

A schema can also limit how long a piece of text may be, set a pattern that a piece of text must follow, and say whether extra arguments are allowed.

Here is the main part of the rule sheet for `get_dock_hours`, which the lab's **Schema check** card shows spread over more lines, along with the tool's name and description:

```text
"parameters": {
  "type": "object",
  "properties": {
    "dock": {"type": "string", "enum": ["north", "south"]},
    "day": {"type": "string", "enum": ["weekday", "sunday"]}
  },
  "required": ["dock", "day"],
  "additionalProperties": false
}
```

You can read it line by line, the way the clerk reads a blank form before anyone fills it in:

- `"parameters"` is the label for the whole rule sheet. The **parameters** are the boxes a tool's form has, and the arguments are what a call writes in those boxes.
- `"type": "object"` says the arguments must be a group wrapped in curly brackets, which JSON calls an object.
- `"properties"` lists the labelled boxes that the group may hold, which JSON Schema calls properties, and here there are two of them, `dock` and `day`.
- Each property must be a string, and `enum` lists the only strings allowed, so the dock must be `north` or `south`, and the day `weekday` or `sunday`.
- `"required"` says that both properties must be filled in, so a call that leaves one out breaks the rules.
- `"additionalProperties": false` says that no other property is allowed, so the form has exactly two boxes and no room for a third.

An **enum** is a rule that a value must be one of a listed set. The word is short for enumeration, which means listing things one by one. A string could hold any text, but an enum turns it into a closed choice, like a café menu where you can order only the dishes printed on it.

Enum matching is exact, so `"North"` with a capital N does not match `"north"`. A person would read those as the same word, but the check compares them letter by letter, and a capital letter is a different letter.

Checking the arguments against the rule sheet before anything runs is called **validation**, and it is the clerk going through every box on the form. Validation can tell whether a request has the right shape, but it says nothing at all about whether a well-shaped request is a good idea.

### One round trip, in ten stages

Now you can follow a whole round trip, which the lab's **Host pipeline** card draws as ten numbered stages. The model's stages sit on the left under the heading “Model — writes text”, and the host's stages sit on the right under “Host program — runs code”. Here are all ten, each starting with the title the lab gives it:

1. **Sends 3 tool schemas with the request:** the host hands the model the conversation so far, with the name, description and rule sheet of each of its three tools.
2. **Reads the tool list in its prompt:** the text a model is given to read is called its prompt, and the tool list is part of that text.
3. **Writes a call as text:** the model writes a function call, such as the one about the north dock above.
4. **Parse the text as JSON:** to parse means to read text and split it into its labelled pieces, and this fails if the text is not proper JSON.
5. **Look up the tool name:** the host checks that the name in the call matches one of the tools it actually offered.
6. **Validate arguments against the schema:** the host checks every argument against the tool's rule sheet, box by box.
7. **Apply host policy:** the host checks its own rules about which tools may run, and whether this one needs a person's approval first.
8. **Execute:** the host runs the tool, which may change something in the world, such as saving a note.
9. **Append the result as a tool message:** the host adds a message saying what happened to the end of the conversation, which is what append means.
10. **Next turn reads the tool message:** the next time the model runs, it reads that message. The lab's note under this stage says “and nothing else about what the host did”, because the tool message is the only way the model learns what happened.

The model's part is stages 2, 3 and 10, and everything else is host code. The host code that runs stage 1 and stages 4 to 9 is often called the **orchestrator**. It is the part of the host that keeps every step happening in the right order, and the host's own rules live inside it.

The message the host adds at stage 9 is called the **tool result**. When everything passes, the tool result holds the tool's answer, which for the north dock on a Sunday is `{"dock":"north","day":"sunday","closes":"16:00"}`. On a 24-hour clock, 16:00 means 4 p.m., so that is when the north dock closes on Sundays.

When a host stage fails, the stages after it do not run, and the lab marks them “– skipped”. Stage 9 still happens, though, because the host always appends a tool message, and when something has failed, that message is an error report instead of an answer.

### Six ways a call can be broken

Each kind of mistake gets caught at a particular stage, and each one produces its own message. The lab has a button for every one of them.

When the host reports a mistake in the arguments, it names the broken box with a short label that starts with a slash, such as `/dock` or `/day`. That label is called a path, and it points to one exact box, the way a street address points to one house on a long road.

Here is what each button's request does wrong:

- **Unparseable text**, the *not JSON* button: the request stops before its closing brackets, like a text message cut off mid-sentence. Stage 4 fails, and the host returns `{"error":"could not parse the tool call as JSON"}`.
- **Unknown tool**, the *unknown tool* button: the user asks “Is it windy at the harbor?”, and the call names `get_weather`, a tool the host never offered. Stage 4 passes but stage 5 fails, and the host's error also lists the three tools it does have.
- **Missing field**, the *missing field* button: the arguments hold a day but no dock. Here a field is another name for a property, one labelled box on the form, and stage 6 reports `/dock` with the words “required property is missing”.
- **Wrong type**, the *wrong type* button: the day is written as the integer `7` instead of a string, so stage 6 reports `/day` with “expected string, got integer”.
- **Bad enum**, the *bad enum* button: the user asks about the east dock, and the call fills in `"east"`. That is a perfectly good string, but it is not one of the two allowed docks, so stage 6 reports `/dock` and lists the allowed values.
- **Extra field**, the *extra field* button: the user adds “It's urgent.”, and the call adds a box the form does not have, `"urgent": true`. Stage 6 rejects it with `/urgent` and the words “property not allowed by the schema”.

For the four argument mistakes, the host wraps every problem it found into one message, such as `{"error":"invalid arguments","details":["/day: expected string, got integer"]}`.

Each of these messages is a **structured error**, which means the failure is written down as data that says where and why. Instead of crashing or quietly refusing, the host always hands back something that the next model call can read.

### Neat is not the same as safe: host policy

Picture a friend asking you to look up the bus times on your phone. You do it without a second thought, because looking something up changes nothing. If they asked you to send a message to everyone in your contacts, though, you would stop and think first, even if they had spelled every word perfectly. The spelling was never the problem, because what worries you is the sending, and you are the one who would press send.

In function calling, the model is the friend who can only ask, and the host is the one holding the phone. The lab's *email the log* button holds a request of exactly that kind. Its user asks to “Email the visitor log to everyone at the harbor,” and the call looks like this:

```text
{"name": "send_email", "arguments": {"to": "all@harbor.example", "body": "Full visitor log attached."}}
```

This call passes stages 4, 5 and 6 without a single problem, because it is proper JSON and it names a real tool. The rule sheet for `send_email` has a pattern rule for the address, which asks for some text, an @ sign, then more text, with no spaces, and this address fits it. The message is also well under its limit of 200 characters, so the rule sheet has nothing to complain about.

The call is stopped at stage 7 by the host's own rules, and rules that the host applies after validation are called **host policy**. They say which tools run automatically, which need a person to approve them, and which are never offered to the model at all. In this lab, `get_dock_hours` and `add_note` run automatically, while `send_email` runs only after a person approves it.

Policy exists because some tools change things in the world, such as saving a note or sending an email. A change like that, caused by running a tool, is called a **side effect**. A side effect happens only if the host runs the tool, and once an email has gone out, nothing the model writes afterwards can take it back.

Policy does not have to treat every side effect the same way, because the people who build the host choose the rules. In this lab, a note stays inside the host's own memory, so it runs automatically. An email leaves the harbor and cannot be called back, so it waits for a person.

Notice what the rule sheet could and could not say about the email. It can say that the address must contain an @ sign and that the message must be short. Nothing about shape can say whether sending a private visitor log to the whole harbor is wise. That is a question about consequences, and the host's policy is where it gets answered.

### What constrained decoding can and cannot do

In Structured and constrained decoding, you saw a way to control a model's writing while it is being written. At every step, the program blocks any next token that would break a set of shape rules, called a grammar, and this blocking is called masking. Writing with masking like this is called **constrained decoding**, and a grammar can be built straight from a tool's JSON Schema.

With a grammar built from this lab's schemas, every one of the six broken requests becomes impossible to write. After the model writes the label `dock`, only `north` or `south` could come next, so `"east"` and `"North"` are blocked. The name could only be one of the three real tools, no extra label could be added, and the text could not stop before its closing brackets.

The email request is different, because it already fits every rule, so the grammar lets every token of it through. A grammar can only ask whether the next token fits the shape, and it has no way to ask whether the request is a good idea. So constrained decoding cannot make a policy decision, and that decision has to happen in the host, after the call is written.

The lab sums this up in a readout called **Grammar blocks it**, which answers whether constrained decoding with these schemas could have stopped the call from being written. In the two error-then-retry examples, which come later, it always describes the first of the two calls.

It reads *yes* for every shape error and *no* for *email the log* when nobody has approved it. It reads *n/a*, short for “not applicable”, when the call ran and there was nothing to stop. The lab does not build or run a grammar to get this answer, because the readout follows a fixed rule based on which stage failed.

### When a call fails, the error comes back as data

When a check fails, the host turns the failure into a tool message. The next model call reads that message as ordinary text, along with everything else in the conversation. Because the error names the path and the reason, the next call can be a new function call with different arguments. This is called a repair loop, and when the model writes its next call, the error message is its only clue about what to change.

Picture handing in a worksheet and getting it back with one note in the margin: “Question 3 needs units.” That note is all you have to go on, so you add the units to question 3 and hand the sheet in again. Your teacher marks the whole sheet again from the top, and if you had written the same answer a second time, it would lose the mark a second time.

If the note had only said “something is wrong”, you would have had to guess which answer to change.

The lab's *wrong type, then fixed* button shows this loop with two calls. The first call writes the day as `7`, so it fails at stage 6, and the tool message reads `{"error":"invalid arguments","details":["/day: expected string, got integer"]}`. The second call, the retry, is the same request with the day written as `"sunday"`, so every stage passes and the tool message reports a closing time of 16:00.

The two calls differ in only one value, and the only thing that pointed at that value was the error message. The host did not change the day for the model, because it never repairs a call. It also checks the retry from scratch, the same way it checked the first call, so if the retry repeats `7`, it fails in exactly the same way.

In this lab, the retry was written by hand to show what a good repair looks like. In a real system the model would write it, and nothing guarantees that the model will fix the right argument, or fix anything at all.

### Where the office picture stops matching

The office with a slot gets the shape of function calling right, but it differs from the real thing in three ways:

- A person understands a reply slip, while a model only produces new text from the text in front of it, so nothing guarantees it fixes the right box.
- A friendly clerk might fix an obvious slip for you, crossing out 7 and writing Sunday. The host never does that, because it only reports problems and leaves the change to the next call.
- A clerk uses judgment, while the host's policy is a set of rules that developers wrote in advance. For some tools it adds a real person saying yes or no, which is what the manager's signature stands for.

## Why it’s here

An earlier lab, Structured and constrained decoding, showed how to make a model's output come out as proper JSON. This lab picks up from there, with everything that has to happen after the text parses and before anything in the world changes.

The basic problem is that text and action are separate things. The model can write the words `get_dock_hours`, but the harbor's timetable lives in a table inside the host. The model cannot read that table unless the host runs the lookup and writes the answer back. Exact arithmetic, a saved note and a sent email work the same way, because the host's code does each of them.

That code is the part of the system that actually does things, so it is the natural place to decide what may happen. That is why parsing, validation and policy all live in the host, and why the order of the ten stages matters: every check comes before the tool runs.

The way the host reports failure matters every bit as much, because a broken call that crashed the program would end the conversation. A call that was refused without a word would leave the next model call with nothing to work from. Returning the error as a tool message keeps the conversation going and gives the next call the one fact it needs.

That design pays off in the next lab, Agents, where the host runs this round trip in a loop with many calls in a row. Every rule from this lab gets applied at every step of that loop. A readable error message is what lets the loop correct itself, instead of failing in the same way again and again.

## How to play with it

The lab's six steps walk you through the ideas in order, and each heading below matches one of those steps. Each button in **Model output** loads a ready-made request, called a preset, and each part below tells you which ones to press and what to look for.

### Read the contract

Here the contract means the tool's rule sheet, the promise about what its arguments must look like. The **Schema check** card's title calls it “The contract the arguments must meet”.

Leave the preset on *valid call*, in the row labelled “well-formed”, so that **Model output** holds the north dock call from earlier in this lesson. The user's line above it asks “When does the north dock close on Sunday?”

Next, read the rule sheet in **Schema check**, whose heading says `get_dock_hours · policy auto`. That means this tool runs without anyone's approval, and below the heading you can find the two enums, the required list and `"additionalProperties": false`.

Then follow the stages in **Host pipeline**, where stages 4 to 8 each show “✓ pass”. Stage 6 adds the note “types, enums, required and extra fields all check out”, which means the arguments obeyed every rule on the sheet. Stage 8 says “read-only lookup; nothing changed”, and stage 9 shows the tool message with `"closes":"16:00"`, which is 4 p.m.

### Break the arguments

Now click *missing field*, *bad enum*, *wrong type* and *extra field* in turn, from the row labelled “malformed”. Each call still parses and still names a real tool, so stages 4 and 5 pass every time, while stage 6 fails and stages 7 and 8 show “– skipped”.

Look at **Schema check** each time, because it lists each broken rule with its path, and compare *bad enum* with *wrong type* in particular. The first says `/dock` must be one of the allowed values and got `"east"`, while the second says `/day` expected a string and got an integer.

The badge at the top of **Host pipeline** reads “not executed” for all four. Nothing ran, so nothing changed, and the only thing the host produced was an error message.

### Break the text

Click *not JSON*, and stage 4 fails because the text stops before its closing brackets, then click *unknown tool*, which fails one stage later. **Schema check** explains that the host offers only `get_dock_hours`, `add_note` and `send_email`, so `get_weather` is not one of them.

**Try this:** Click *valid call*, then go into **Model output** and change `"north"` to `"North"`. The label above the box now says the text was edited by you, and every check runs again on what you typed. Stage 6 fails with `/dock`, because enum matching is exact and the capital N is a different letter.

Then change the dock to `"south"` instead, and every stage passes, with a tool message reporting that the south dock closes at 21:00, or 9 p.m. Keep that result in mind, because the user asked about the north dock, and nothing in the lab flagged the difference.

You can also break two rules at once by changing the dock to `"east"` and the day to `7`. Stage 6 then reports “2 errors”, because the host checks every argument and reports a problem for each one, instead of stopping at the first broken argument. If a value is the wrong type, though, the host reports only that, and does not go on to check it against the list of allowed values.

### Valid is not safe

Click *email the log*, and you will see stages 4, 5 and 6 all pass while stage 7 fails with “send_email needs a human approval — none given”. The tool message tells the model the same thing in JSON: `{"error":"send_email needs human approval; none was given"}`.

Now set **Approve send_email** to *human approves*, and watch stages 4 to 6 stay exactly the same while stage 7 now passes. Stage 8 then runs and reads “Host queued an email to all@harbor.example (simulated; nothing leaves this app)”, so only the policy stage changed the outcome.

For comparison, click *add a note*, where the user says “Remind me to bring the dog's tag.” This tool runs without approval, and stage 8 shows its side effect, “Host saved note #1”, along with the note's words.

Before you move on, set **Approve send_email** back to *no approval*. Picking a new button does not reset it, so if you leave it on, *email the log* will keep running in the steps that follow.

### Read the transcript

Open **Transcript**, whose heading says it shows “What the next model call receives”. It lists the messages in order, starting with a system message, which is the host's own setup text, here listing the tools, and then the user's question. Next comes the assistant's call, meaning the model's text exactly as written, and then the tool message from the host.

The last line reads “next call: generated from the four messages above”. That line is only a placeholder, because no model runs here, but it marks where a real model would read those four messages and write its next turn.

Below the messages sit three readouts, and each one answers a different question about the exchange. **Executed** says whether the last call ran, **Grammar blocks it** says whether constrained decoding could have stopped the first call, and **Calls made** counts the calls in this exchange.

With **Approve send_email** set to *no approval*, compare *missing field* with *email the log*, and you will see that both show **Executed** as *no*. **Grammar blocks it** reads *yes* for the missing field but *no* for the email, because a grammar can stop a broken form but not a neat, risky one.

### Repair a bad call

Click *wrong type, then fixed*, from the row labelled “error, then retry”. **Model output** now has two boxes, one for turn 1 holding `"day": 7` and one for turn 2 holding `"day": "sunday"`. The second box's label says “authored retry; sent only if turn 1 fails”, where authored means it was written by hand rather than by a model.

A new control called **Turn** appears in **Host pipeline**, and it chooses which of the two calls the stages show. Set it to *1 · first call*, and the heading reads “Turn 1 of 2 · stopped at validation”, with stage 6 failing on `/day`. Set it to *2 · retry*, and the heading reads “Turn 2 of 2 · get_dock_hours ran on the host”, with every stage passing.

**Transcript** now shows both turns, with the error message sitting between the two calls. Its last line says the next call would be generated from the six messages above, and **Calls made** reads 2. **Executed** reads *yes*, because it describes the last call, which is the retry. **Grammar blocks it** still reads *yes*, because it always describes the first call.

Now edit the turn 2 box so that it repeats `"day": 7`. The heading for turn 2 changes to “stopped at validation”, because the host checks every call from scratch and gives the retry no special treatment.

Last, change the turn 2 box back to `"sunday"`, and then fix the turn 1 box too, changing `7` to `"sunday"`. The first call now runs, so the retry is never sent: the **Turn** control disappears, and **Transcript** goes back to four messages. The *missing field, then fixed* button works the same way, except that the first call leaves out the dock.

## What to notice

- The model's stages, 2, 3 and 10, never show a pass or fail mark, because they are not checks. The model only reads and writes text, and every check happens in the host's code.
- There are two different kinds of problem here, and the lab's rows of buttons sort them for you. The six malformed requests are broken forms, while *email the log* is a perfectly filled-in form that asks for something risky.
- **Grammar blocks it** reads *yes* for every broken form and *no* for *email the log*. A grammar can control shape, but it cannot judge whether a request should run.
- Every failure still produces a stage 9 message, so the conversation carries on and the next call reads an error report instead of an answer.
- The tool message is the only record of what the host did that the next call ever sees. A note saved by *add a note* exists only in the host's memory, and the model meets it only as `{"saved":true,"note_id":1}`.
- In the retry presets, the two calls differ in one value, and only the error message pointed at that value, while the host fixed nothing itself.
- A retry is checked like any other call, so repeating a mistake fails in the same way. If the model kept writing the same broken call, a loop with no limit would keep failing for as long as it was allowed to. That is why the next lab gives the loop a step cap.
- The host checks your edits in exactly the same way as the prepared requests, because it does not know or care who typed the text in the box.

## Where it breaks

### In this lab

The lab fakes or simplifies several things, and it is worth knowing exactly which ones before you trust what it shows.

- All eleven first calls were written by hand: three well-formed, six malformed, and two that fail and then get a retry. The two retries were written by hand too, so neither of them was produced from the error text.
- No model is used at any point, so the lab cannot tell you how often a real model writes a bad call, or whether it would repair one.
- The checker covers only part of JSON Schema: types, enums, required properties, extra properties, text length and text patterns, such as the email address rule. It has no rules for lists of values or for a schema that points to another schema, and none of this lab's tools has a group inside a group.
- The **Grammar blocks it** readout is a simple rule based on which stage failed. No grammar is actually built or run, so it shows what constrained decoding could stop, not a test of it.
- The tools are a small table of closing times, a note counter and an email that never leaves the app, so nothing reaches the internet or the computer's files.
- Each turn holds one call, so there are no parallel calls and no arguments arriving piece by piece while the model writes. A retry happens only in the two retry presets, and only once.
- The messages are labelled with general role names such as system, user, assistant and tool, while real services name and arrange them in their own ways.
- The last line of **Transcript** is a placeholder, because the lab never generates the next call or a final answer.

### In real systems

The real mechanism has limits of its own, even when every part of it is built carefully.

- **Running every valid call is a host bug**, because if the orchestrator does that, a perfectly tidy request can still delete files or send private data out.
- **Arguments can have the right shape and still be wrong**, since a valid dock name can still be the wrong dock. Validation checks shape, not whether the call matches what the user asked.
- **Tool results cannot be trusted blindly**, because a web page or an email returned by a tool becomes text that the next call reads. That text can contain instructions, such as a line telling the model to ignore its earlier ones.
- **Rule sheets differ between services**, because each AI company's service accepts its own part of JSON Schema. Some services also offer a strict setting, which forces the arguments to match the schema, and that setting adds rules of its own.
- **A repair loop only sees the errors the host notices**, and a call to the wrong dock passes every check, so there is no error to read.

Picture asking a friend in a group chat to check when the north dock closes, and they check the south dock by mistake. They send back a real closing time for a real dock, so nothing about the reply looks broken, and nobody will notice unless they compare it with the question. The *south* edit from the walk-through above is that friend, and the host passes it without a murmur.

Even when the host does catch an error, nothing guarantees that the model will fix the right argument, or fix anything. An error message that only says “failed” gives the next call almost nothing to work from. A loop that keeps failing will repeat for as long as the host allows it.

**A common mix-up:** people often say that “the model sent the email”, or that the model ran a tool. The model only wrote a request, which is a piece of text, and it was the host program that sent the email, or refused to send it.

## Going deeper

### How models learn to write calls

Models learn to write tool calls during post-training, a later stage of training in which they learn from examples of calls and the results that came back. An early research study called Toolformer, from 2023, looked at a model learning when to call a tool. Another, called ReAct, from 2022, had a model mix written reasoning with actions and with what those actions returned.

Today, programmers connect their own programs to chat services through an API, which is the set of commands a service accepts from other programs. These services accept tool definitions written in JSON Schema, and they return the model's calls in a separate part of their reply. Many offer a strict setting that uses constrained decoding, so the arguments always match the schema.

None of these features moves the running of tools into the model, because the host still decides what runs.

### Descriptions and tool choice

The description is the part of a tool that the model reads as ordinary prose, so it does much of the work of picking which tool a call names. Anthropic's documentation for its Claude service, in a page called Define tools, calls detailed descriptions “by far the most important factor in tool performance”.

That page asks for a description to say what the tool does, when to use it and when not to, and what each argument means. It gives “Gets the stock price for a ticker.” as an example of a poor one, because it leaves out nearly all of that. A ticker, in case you have not met the word, is the short code that names a company on the stock market.

Because the description does much of the work of picking, two tools with vague descriptions that overlap make it more likely that a call names the wrong one. This lab measures nothing like that, because its three tools are clearly different from one another.

The same documentation describes a tool-choice setting with four modes, which control whether a reply has to call a tool:

- In `auto` mode, the model's reply may call a tool or may answer without one.
- In `any` mode, the reply must call one of the tools, though it can be any of them.
- In `tool` mode, the reply must call one particular tool that the host names.
- In `none` mode, the reply cannot call a tool at all, so the model has to answer in ordinary text.

Such a setting limits what the model may write, but it does nothing to make the arguments right.

### Parallel calls

Some services let the model write several tool calls in a single turn, which are called **parallel tool calls**. Anthropic's documentation, in a page called Parallel tool use, says the host chooses whether to run them all at once or one after another.

Calls that only read information and do not depend on each other are usually safe to run at the same time. Tools with side effects, or tools that need to happen in a set order, may be better run one at a time. Either way, each call still gets its own result message, while this lab handles only one call per turn.

### Shared standards: the Model Context Protocol

The **Model Context Protocol**, or MCP, is an open standard, which means a published set of rules that anyone may use. It connects an app to tools and other information held by separate programs called servers, where a server is a program that waits for requests and answers them.

MCP sends its messages in a fixed format called JSON-RPC 2.0, which sets out how a request and its answer are written. A server lists its tools in reply to a message called `tools/list`, giving each one a name, a description and its JSON Schema. The schema is stored under the label `inputSchema`, and the app then calls a tool with a message called `tools/call`.

The specification's Tools page separates two kinds of failure, treating an unknown tool or a badly formed request as a protocol error. A protocol error comes back as an error in the JSON-RPC format itself, rather than inside a tool result. A problem such as invalid input counts as a tool error instead, and it comes back inside the result, marked `isError: true`.

The specification says apps should pass those tool errors to the model so that it can correct itself, which is the same repair loop this lab shows. It also says hosts must get a person's clear permission before running any tool at all. That rule is stricter than this lab's policy, which lets `get_dock_hours` and `add_note` run without asking anyone.

This lab does not use MCP, so there is no server, no JSON-RPC and no tool listing. Its three tools are built into the lab, and every failure, including an unknown tool, comes back as the same kind of tool message. What the lab does show is the host's side of the loop, which any such standard still leaves to the host.
