## The big picture

You have probably typed a question into a chatbot and seen one reply come back, all at once. Some AI systems go further. They look things up, read what comes back, and try again when something goes wrong. Only then do they give you an answer. A system that works this way is called an **agent**. This lab opens one up so you can watch every step.

Here is the surprise: an agent is not a new or smarter kind of AI. The model inside it can be the very same one a chatbot uses. A second program, wrapped around the model, turns it into an agent. That program runs the same few steps in a loop. Each time round, it asks the model what to do next and does it. Then it writes down what happened and checks whether to stop.

Agents are used for jobs where one request turns into many steps. Examples are researching a question or working on computer code. One AI company, Anthropic, has described a research agent that splits a big question into pieces. It hands those pieces to helper agents.

Without a loop, the model gets a small, fixed number of turns. It can ask for one lookup, read what comes back and reply, and then it is over. The loop removes that limit, so the model can keep looking things up as long as needed.

That freedom brings new trouble. The loop needs a way to stop, it costs more the longer it runs, and mistakes can pile up. So this lesson covers how the loop ends and what it costs, as well as how it works.

By the end of this lesson, you will be able to explain these five ideas in your own words:

- Why an agent is a loop wrapped around an ordinary model, not a special kind of model.
- The three ways the loop can end, and what happens when only a limit on steps is left.
- Why each step reads more text than the last, so cost grows faster than the number of steps.
- How to work out the chance that a long run gets every step right. Also how a check partway through raises that chance, at the cost of redone work.
- The difference between repeating a failed request and fixing it after reading the error. Also which of the two a rule against repeated failures can stop.

The lab is set in a harbor, where an assistant answers questions about docks, ferries and wind. The **Agent loop** card draws the loop as a diagram. It lets you replay a run one event at a time. **Trace** lists every message in order, and **Budgets** sets the limits that end a run. **Context growth** shows how much text each step has to read before it can write anything.

The last card, **Reliability**, works like a calculator. You choose how often each step goes right and how long the run is. It then shows how often the whole run comes out right. It does this with and without a person checking the work partway through. Its numbers come from a formula, not from running an agent.

The model in this lab is not a real AI. Its choices follow a short script written in advance, but everything around it is computed for real. That means the loop, the tools, the limits and every count of text read.

## What it is

### The model writes, the host acts

The model inside a chatbot does one thing: it reads text and writes more text after it. It cannot click a button, open a website or check a timetable on its own. Another program runs the model and does anything that has to happen in the world. This lab calls that program the **host**.

The host offers the model a few **tools**. A tool is a small program that the host will run, like one that looks up dock closing times. To use a tool, the model writes a request in a strict text format. The request names the tool and fills in the details it needs. That request is called a **tool call**. Here is the exact one that the lab's first task writes:

```text
{"name": "get_dock_hours", "arguments": {"dock": "north", "day": "sunday"}}
```

The details inside it, here the dock and the day, are called **arguments**. That is why one of the lab's tasks is named *Fix an argument*. The model only writes this text, while the host reads it, runs the tool and gets the result.

### The agent loop

An **agent** is a model plus a host that asks it the same kind of question again and again. The host code around the model makes the agent, and nothing new sits inside the model. So the model can be the same one used for chat. Each time round the loop, the host goes through the same five steps, in this order:

1. The host gathers everything written so far into one block of text. The model reads it from start to finish.
2. It hands that text to the model, which writes back one thing: a final answer or a tool call.
3. If the model wrote an answer, the loop ends and the host passes the answer to the user.
4. If the model wrote a tool call, the host adds it to the bottom of the text. It runs the tool and adds the result below.
5. The host checks its limits and, if they allow another turn, goes back to step 1 and starts again.

This cycle is called the **agent loop**. The growing record of every message, in the order written, is called the **transcript**. On every call the model reads the whole transcript. So the diagram's first box is labeled **Context**, which means the text the model reads this time.

Here is the loop at work on the first task, *Look up hours*. The user asks, “When does the north dock close on Sunday?” Model call 1 reads the transcript, which so far holds the host's instructions and that question. It writes the tool call shown above. The host runs the tool, which reports that the dock closes at 16:00, or 4 p.m. The host adds that result to the transcript.

Model call 2 reads everything again, including that result. It writes, “The north dock closes at 16:00 on Sundays,” and that ends the loop after two calls.

### Observations: the model's only news

The result the host adds after running a tool is called an **observation**. It can be a useful answer, such as a closing time, or it can be an error. One error in this lab reads “timeout after 5 s”. That means the tool took too long, so the host stopped waiting after five seconds.

Either way, the observation is the only way the model learns what happened. The model never sees the tool run. The model also remembers nothing from one call to the next. Suppose the host did not write the observation into the transcript. Then the next call would have no sign that the tool had ever run.

### Three ways to stop

A loop needs a way out, and this one has three. You can trigger all of them in the lab:

- **Terminal action:** the model writes a final answer instead of a tool call. “Terminal” means “last”, like the terminal at the end of a bus line.
- **Step cap:** this is the most model calls the host will make in one run. Once they are used up, the host refuses to call the model again.
- **Stop rule:** this is a check in the host's code. It ends the loop early when a run looks stuck. Here it fires when the same tool call fails twice in a row.

Only the first of these ends with an answer. The other two are the host stepping in, and they leave the question unanswered.

This matters most when the model keeps writing tool calls and never writes an answer. The model can only end the loop by answering. So if no stop rule is switched on, the step cap is the only limit left. The loop keeps going until every allowed call is used, and each call reads more text than the last. Then it stops with no answer at all.

### An analogy: the advisor and the runner

Picture a harbor office with two workers who split the job. The advisor sits in a back room with no phone and can only write. The runner sits at the front desk with the phone and the customers.

Each turn, the runner hands the advisor a notebook that holds everything so far. The advisor reads it from the very first page. Then the advisor writes one line at the bottom. That line is either an answer or a request, such as “phone the dock office and ask about Sunday.”

If the line is an answer, the runner passes it to the customer and the job is done. If it is a request, the runner makes the call and writes down what they heard. Then the runner checks the office rules before handing the notebook back. One rule limits how many turns a job may take. Another says to stop if the same request fails twice in a row.

In this picture, the advisor is the model, the runner is the host and the notebook is the transcript. Each line the runner writes down is an observation. The office rules are the step cap and the stop rule.

The analogy stops matching in two places. First, a person handed the same notebook again would skip the pages they had already read. A model re-reads every word on every call, and each re-read has a cost. The next part of this section measures it.

Second, a real advisor understands the notebook, while a model is a program that turns text into more text. The “advisor” in this lab is something simpler still, as the last part of this section explains.

### Every call re-reads everything

To measure reading, the lab counts **tokens**. A token is a small chunk of text that a model reads at one time. It can be a word, part of a word, a number or a punctuation mark. Reading more tokens takes more work, and real services charge for it. So the number of tokens read is this lab's measure of cost.

The lab counts tokens with a toy rule. Every unbroken string of letters, such as a word, counts as one token. So does every unbroken string of digits, such as 16, and every single symbol. By that rule, the question “When does the north dock close on Sunday?” is 9 tokens. That is eight words plus the question mark. A time such as 16:00 counts as 3 tokens. The hours, the colon and the minutes each count once.

Each call's input starts with a fixed base. The base is the host's opening instructions, called the **system prompt**, plus the user's question. The system prompt tells the model that it is the harbor assistant. It also lists the tools the model may call, one at a time. After the base comes every earlier call and result. So the input gets bigger each time the loop goes round.

The task *Retry forever* shows this most clearly, because every one of its turns adds exactly the same text. Its base is 58 tokens. Each failed turn adds 31 more, made up of the tool call and the error message that comes back. So the first four calls read these amounts, and each one pays again for everything before it:

- Call 1 reads only the base, which is 58 tokens, because nothing has happened yet.
- Call 2 reads the base plus one earlier turn, so it reads 58 + 31 = 89 tokens.
- Call 3 reads the base plus two earlier turns, which comes to 120 tokens in all.
- Call 4 reads the base plus three earlier turns, which comes to 151 tokens in all.

Added together, those four calls read 418 tokens. That is the number **Tokens read** shows at a cap of 4.

Now draw each call's earlier turns as a row of blocks. The rows are zero, one, two and three blocks long, so they make a triangle. A triangle with 4 rows holds 0 + 1 + 2 + 3 = 6 blocks. One with 8 rows holds 0 + 1 + 2 + … + 7 = 28 blocks, which is more than four times as many. Doubling the rows more than quadruples the blocks, the same pattern you see when you square a number.

That is why the total reading grows much faster than the number of calls. Allowing ten calls instead of four gives two and a half times as many calls. But the total reading jumps to 1,975 tokens, almost five times as much.

The triangle itself grows even faster. With ten calls it holds 45 blocks instead of 6, which is seven and a half times as many. So why does the total grow only about five times? Every call also reads the same 58-token base. That part grows only as fast as the number of calls. Mixing the two slows the total down a little:

- The base comes to 10 × 58 = 580 tokens.
- The earlier turns come to 45 × 31 = 1,395 tokens.
- Together they make 580 + 1,395 = 1,975 tokens in all.

So the total grows much faster than the number of calls, but not as fast as the triangle alone.

This effect is called **context growth**. The card with that name draws it as a row of bars, one for each call. Each bar is one call's input, split into two parts. A faded part stands for the system prompt and user message. A solid, full-color part stands for earlier calls and tool results. The key under the chart names each one. Along the row, the solid part grows from bar to bar while the faded part stays the same.

Calls that the cap allowed but the run never used show up as short, flat markers. The key labels them “allowed but unused”. The chart also follows **Replay step** on the **Agent loop** card. Move it back, and the bars for calls the replay has not reached yet are dimmed. They return to full color as you move forward again.

### Retry or repair

When a tool call fails, there are two very different ways to try again. The difference decides whether a stop rule can help.

Picture a friend logging in to a game. They type their password, see “wrong password”, and type exactly the same thing again. That is a **retry**: the same request sent again in the hope of a different result. This time the screen says “wrong password: Caps Lock is on”. So they switch Caps Lock off and type the password in small letters, and it works. That is a **repair**, because they read the error message and changed what they sent to match it.

A retry is the right move when a failure was bad luck. In *Recover from error*, the ferry tool times out once, and then the same call works. A retry is useless when the failure is built into the request itself, because repeating it can never succeed. In *Retry forever*, the model keeps asking for a wind tool that the host never offered. No number of repeats will change that.

A repair needs an error message that says what went wrong, and *Fix an argument* shows one. Its first call asks about the south dock with the day written as “Weekday”, with a capital W. But the tool only accepts “weekday” or “sunday” in small letters. So the host sends back an error that names the day input and lists the values it allows.

The error writes the day input as `/day`, where the slash points at one part of the request. The second call reads that note and sends “weekday” instead, and this time the tool returns the closing time.

The two also look different to a stop rule. The rule in this lab counts identical failures, meaning the very same call failing twice in a row. It can end a loop of retries, because a retry sends the same call again. It can never end a loop of repairs, because each repair changes the call. Suppose a repair kept changing the call and kept failing. The rule would never fire, and only the step cap would stop it.

### Small mistakes multiply

Even when every tool works, a long run can still fail. Each step is another chance for something to go wrong. The **Reliability** card gives every step the same chance of coming out right. It calls that number **Per-step success**.

Picture a quiz with 20 questions where you get each answer right 95% of the time. A perfect score feels almost certain, yet most of the time you will not get one. A perfect score needs every single answer to be right at the same time.

To see why, picture a large number of runs starting at once. Of those, 95% get step 1 right. Of those, 95% also get step 2 right, and 95% of 95% is 0.95 × 0.95 = 0.9025, or about 90%. Each new step multiplies the chance by 0.95 again. So the chance of a fully right run keeps shrinking as the run gets longer:

- With 2 steps, about 90% of runs come out right from start to finish.
- With 10 steps, about 60% of runs come out right from start to finish.
- With 20 steps, the chance is 20 copies of 0.95 multiplied together, which is about 36%.

So the 20-question quiz gives you only about a 36% chance of a perfect score. Each answer felt safe, but the chances multiply. An agent that is right 95% of the time per step does no better. It finishes a 20-step run with no mistakes only about 36% of the time. The card shows that as 35.8% under **Completes end to end**. That is the chance that a run gets every one of its steps right.

This effect is called **compounding error**, and a fully right run needs every step to go right. So each step, early or late, is one more chance to slip, and the chances multiply. A small chance of error at each step becomes a large chance that the whole run goes wrong. In a real agent it is often worse, because the steps after an early slip build on it.

The multiplying also works in your favor, though. Raising the chance per step from 95 out of 100 to 99 out of 100 looks small. But now 0.99 is the number multiplied 20 times. Twenty copies of 0.99 multiplied together come to about 0.818. So a 20-step run comes out fully right 81.8% of the time, more than double what it was.

### A check partway through: the approval gate

One way to fight compounding error is to have a person look over the work partway through. That check comes before more steps get built on top of it.

Picture a group project with a long report. Your teacher offers to read the first half before your group writes the rest. Suppose the teacher spots a mistake, so your group rewrites the first half, which costs time. But the second half now has a better chance of resting on correct work. The rewrite can still contain new mistakes, because nobody checks it a second time. And if the teacher misses a mistake, it stays. Everything you write next is built on top of it.

In an agent, a point where a person reviews the work so far is called an **approval gate**. The agent waits there before it goes on. The **Reliability** card lets you place one after any step, with **Approval gate after step**. You also set how often the reviewer catches a wrong run, with **Reviewer catches**. In the card's version, a run that gets caught redoes the steps before the gate once. The redo is not checked again.

Here is how a gate after step 10 works out at 95% per step on a 20-step run. The reviewer catches every wrong run:

1. About 60% of runs get the first 10 steps all right. They pass the gate without being sent back.
2. The other 40% reach the gate with a mistake. The reviewer catches all of them, so they redo the first 10 steps.
3. About 60% of those redos come out right, which rescues 60% of 40%, or about 24% of all runs.
4. Adding the two groups together, about 84% of runs leave the gate with a correct first half.
5. The last 10 steps still have to go right, which happens about 60% of the time. And 60% of 84% is about 50%, so about half of all runs come out right.

The card shows that figure as 50.2% under **With the gate**. The same run with no gate at all gets 35.8%.

The price is extra work, because the runs that get sent back do some of their steps twice. About 4 in every 10 runs redo 10 steps, which is 40 extra steps for every 10 runs. Shared out evenly, that is 4 extra steps per run on average. That is why **Expected steps run** reads 24.0 with the gate, instead of 20.0 without it.

A gate placed later protects more steps but sends back more work when it catches something. A reviewer who never catches anything adds no protection at all.

### What stands in for the model here

The **Agent loop** card carries a badge that says **scripted policy**. It tells you something important about this lab. A policy is the rule that picks the model's next message. “Scripted” means someone wrote the rule ahead of time, so it does not come from a real model. This rule says that if the last tool result worked, the model answers. Otherwise it sends the same tool call again.

One task, *Fix an argument*, uses a different rule. It reads the error note from the last tool result and corrects the input that the note names. Neither rule is a real model, but the rest of the page is computed for real. That includes the loop, the tools, the step cap, the stop rule and every token count.

The **Reliability** card has a different badge, **closed-form formula**. It means the card's numbers come straight from formulas like the ones worked through above. They do not come from running an agent.

## Why it’s here

The Tools and function calling lab showed one round trip. The model writes a tool call, the host runs it, and the result comes back. Many real jobs need a whole chain of these round trips. Each one depends on the one before it. Think of a job like this: you look something up and the tool times out. Then you try again and use that answer to look up a second thing.

A single round trip cannot cover that. The host needs a loop that hands each result back and asks the model again. But a loop creates four problems that a single call never had. Each of them shows up on one of the lab's cards:

- **Errors can repeat:** a failed call can be sent again and fail again, forever, unless the host notices. **Trace** shows each failed tool result as an outlined row.
- **Costs grow every turn:** each call re-reads a longer transcript, so later turns cost more than early ones. **Context growth** shows this as bars that get taller.
- **Mistakes pile up:** a long run has many chances to go wrong, and later steps build on earlier mistakes. **Reliability** shows this as the chance in **Completes end to end** shrinking.
- **Something has to say stop:** the model may never write an answer, so the host needs its own limits. **Budgets** holds those limits and shows the **Stop reason**.

How many steps the loop is allowed to take is called its **horizon**. You set it on the **Budgets** card, whose small heading reads “Horizon and stop rules”. A longer horizon lets harder jobs finish. But it also gives errors, costs and unwanted changes in the world more room to pile up.

## How to play with it

### Walk a successful loop

Leave **Task** on *Look up hours*. Notice that **Replay step** starts at the end of the run, where the whole story is already shown. Drag it back to the start, where it reads 1/4 · Model call 1. Then move it forward one event at a time:

- At 1/4, the **Context** box, the **Model call** box and the “final answer?” diamond light up. The line under the diagram says call 1 reads 56 tokens.
- At 2/4, **Host runs the tool** and **Host check** light up. The host runs the call, adds the result and checks the step cap.
- At 3/4, call 2 reads 118 tokens, more than twice as many as call 1. The transcript now holds the first call and its result.
- At 4/4, the run leaves through **Stop · answer**, which the diagram labels terminal action. Call 2 wrote a final answer instead of a tool call.

The two dashed boxes, **Host runs the tool** and **Host check**, are host code. The **Model call** box is marked “writes text only”. You can also click any row in **Trace** to jump **Replay step** straight to that event. That makes comparing two calls quicker.

### Cap the horizon

**Try this:** before you touch anything, guess what happens if the host allows only one model call. Then set **Step cap** to 1. The host still runs the tool that call 1 asked for, so the result, 16:00, lands in the transcript. But **Host check** says stop, because a second call is not allowed. The run leaves through **Stop · step cap** instead of **Stop · answer**, and **Stop reason** reads step cap.

The tool result, 16:00, sits in the transcript where no call will ever read it. So no answer is written.

### Recover from an error

Set **Step cap** back to 4 and **Task** to *Recover from error*. Here the user asks when the afternoon ferry leaves. In **Trace**, call 1 asks for `get_ferry_time`. The host replies with a timeout, which the row outlines as a failure. Call 2 sends exactly the same call, which makes it a retry. This time it gets back 15:40, or 3:40 p.m. Call 3 answers, so the run ends with a terminal action, and **Tool runs** reads 2 (1 failed).

### Loop without a stop rule

Set **Task** to *Retry forever*, where the user asks for the wind speed at the harbor right now. Then slide **Step cap** to 10. The policy asks for `get_wind`, a tool that was never on the host's list. So the host replies “unknown tool get_wind” every time. All ten calls fail, and the run ends by step cap without ever producing an answer.

Now look at **Context growth**, where each bar is taller than the last. The bars rise from 58 tokens for call 1 to 337 tokens for call 10. That last call reads almost six times as much as the first, though both send the same request. The heading adds every bar together to give 1,975 tokens read in total. **Tokens read** in **Budgets** shows the same number, but it writes it without the comma, as 1975.

Set the cap back to 4 and the total drops to 418. So the last six calls cost far more than the first four did.

### Add a stop rule

Keep *Retry forever* and set **Stop rule** to *stop after 2 identical failures*. Then watch how quickly the run ends. The host now stops after two calls and 147 tokens read, whatever the step cap says. The same call failed twice in a row. The diagram exits through **Stop · host rule**, and **Stop reason** reads host stop rule.

Then switch **Task** to *Recover from error* with the rule still on. The run still answers on call 3. One failure followed by a success is not two failures in a row. So the rule leaves this run alone. The rule is a bet, though, because it cannot tell a hopeless repeat from a useful one. It allows one repeat, which is enough for a one-off timeout. But it would also stop a tool that happened to time out twice by bad luck.

### Repair an argument

Keep the stop rule on and set **Task** to *Fix an argument*. Here the user asks when the south dock closes on a weekday. Follow the run in **Trace**, where each row shows one message in the order the host wrote it:

- **Call 1:** this call sends `"day": "Weekday"` with a capital W, a value the tool does not accept.
- **The error:** the host rejects the call. The error names `/day`, lists the allowed values `"weekday"` and `"sunday"`, and quotes the `"Weekday"` it got.
- **Call 2:** this call reads that note and sends `"weekday"` instead. The host returns a closing time of 21:00, or 9 p.m.
- **Call 3:** this call writes the answer, “The south dock closes at 21:00 on weekdays.” The run ends with a terminal action.

The whole run takes 3 model calls and reads 391 tokens, and **Tool runs** reads 2 (1 failed). Only one call failed in this run, so the stop rule had nothing to stop.

Look at the two calls anyway by comparing call 1 and call 2 in **Trace**. They differ only in whether the day starts with a capital letter. So even if call 2 had failed too, the rule would not count it as the same failure repeated. A loop of repairs that keep changing the call and keep failing would slip past this rule. Only the step cap would end it.

### Compound the error

Find the **Reliability** card. Leave **Per-step success** at 95% and **Steps in the run** at 20, and read **Completes end to end**. It shows 35.8%, and next to it, **Longest run that finishes half the time** reads 13 steps. So at 95% per step, only runs of 13 steps or fewer are fully right more often than not.

Now raise **Per-step success** to 99%, and **Completes end to end** jumps to 81.8%. The longest run that finishes half the time stretches to 68 steps. The solid line in the chart tells the same story. It shows the chance of a fully right run falling as the run gets longer. At 99% that line falls much more slowly, which is why far longer runs stay above the halfway mark.

Set **Per-step success** back to 95% and try the approval gate. Watch the dashed line that the chart adds for the run with a gate:

- Set **Approval gate after step** to 10, with **Reviewer catches** at 100% of wrong runs. **With the gate** reads 50.2%. **Expected steps run** rises from 20.0 to 24.0, because some runs now redo their first half.
- Lower **Reviewer catches** to 0%, and **With the gate** falls back to 35.8%. A reviewer who never catches anything never sends anything back.
- Put **Reviewer catches** back to 100% and move the gate to step 1. **With the gate** reaches only 37.6%, because the gate protects one step out of twenty.
- Move the gate to step 20, the end of the run. **With the gate** reaches 58.8%, the highest so far. The catch is that **Expected steps run** climbs to 32.8, because a caught run now redoes all 20 steps.

## What to notice

- The model never ends the loop except by writing an answer. Every other way out, the step cap and the stop rule, lives in the host's code.
- A step cap makes sure the loop ends, but it does not make sure you get an answer. A run stopped by a limit leaves the question unanswered.
- Every call re-reads the whole transcript, so each call reads more than the last. On *Retry forever*, each turn adds the same 31 tokens. The total grows much faster than the number of calls. Raising the cap from 4 to 10 makes it almost five times bigger.
- The stop rule leaves *Recover from error* alone. One failure followed by a success is not two identical failures in a row.
- A retry repeats the call, while a repair changes it after reading the error. A stop rule on identical failures can end a loop of retries. It cannot end a loop whose calls keep changing.
- Small losses at each step multiply. Going from 95% to 99% per step more than doubles the chance of finishing all 20 steps.
- A gate protects only the steps before it, and it costs redone work. Its value depends on where you put it and how often the reviewer catches mistakes.

## Where it breaks

### In this lab

This lab is a simplified model of an agent, and here are the places where its simplifications show:

- The model is a fixed rule, the scripted policy. A real model picks its words with some chance involved. It could answer early or choose a different tool. It could also write a reply saying it cannot find the answer. That ends the loop as a terminal action.
- The repair in *Fix an argument* is a matching rule. It compares the wrong value with the allowed values in the error note, ignoring capital letters. It does not understand the note, so a real model could misread it and repair the call wrongly.
- The tools return fixed values. The ferry tool fails on its first try on purpose, so you can watch a retry work.
- Token counts use the toy rule. A real model splits text with a method called a **tokenizer**, so its counts differ.
- Nothing is saved between calls to make re-reading cheaper. That trick is called prompt caching, and Going deeper describes it. Nothing runs side by side either, so every call waits for the one before it.
- The **Reliability** card is a formula, not a run of an agent. **Per-step success** is a number you choose, not a measurement of a real agent.

The formula behind that card also rests on assumptions that real runs often break. These are the main ones:

- Every step has the same chance of going right. One step going wrong does not change the odds for the next.
- The agent cannot see its own wrong steps, so it never notices a mistake or fixes one by itself.
- There is one reviewer, and a run that gets sent back is redone once without a second check.

### In real systems

- **Errors compound:** say each step is right 95% of the time. A 20-step job is then fully right only about 36% of the time. Real steps are not all alike, because some are much harder than others. One mistake can also make the next more likely. So you have to measure a real agent's per-step rate on its own tasks instead of guessing it.
- **Reviewers miss errors:** an approval gate helps only as far as the reviewer catches wrong work. A reviewer can miss a mistake or be skipped when time is short.
- **Plans are only text:** some agents write out the steps they plan to take before or between actions. This is called **planning**. A plan is text the model wrote, so nothing forces later calls to follow it. A longer plan also has more steps to get right.
- **Observations can mislead:** a tool can send back text that is out of date or incomplete. It can even be hostile, meaning written on purpose to trick the model. The next call reads that text like everything else in the transcript.
- **Changes in the world add up:** each step can do something real. Examples are sending a message or deleting a file. A long loop that can change things needs permissions and a person's confirmation, not only a step cap.
- **Long transcripts cause trouble:** they cost more to re-read. They can also bury early details that the model needs later. They can also grow past the **context window**. That is the most text a model can take in on a single call.

**A common mix-up:** many people think a longer loop means a smarter agent. They picture extra steps making the model cleverer. The model inside is the same on call 10 as on call 1. More steps only give it more chances to finish. They also give it more chances to repeat a mistake, spend more and change things you wanted left alone. On *Retry forever*, raising the cap from 4 to 10 bought six more failures. It also bought almost five times the reading, and it still found no wind speed.

## Going deeper

Most agent frameworks still run a loop like this one and add extras around it. A framework is a ready-made toolkit that people use to build agents. Typical extras are memory, written plans, more than one model, and helper agents. Each helper takes part of a job. A 2022 research method called ReAct helped make this style popular. It mixes the model's written reasoning, its actions and the observations into one transcript.

Real agents are limited by more than a step cap. They also get limits on time, on money spent and on which tools are offered. Many also ask a person before an action that cannot be undone, such as deleting something for good.

Some services can store the unchanged start of a transcript so that re-reading it costs less. This is called **prompt caching**. Even with it, the transcript still grows on every turn. The other problems of a long transcript stay too.

### Memory

What an agent can use beyond the current call is called its **agent memory**. It has two quite different kinds. Its working memory is the transcript the loop re-reads on every call. That memory is exact but limited by the context window, and it keeps growing. An **external store** sits outside the transcript. It can be a file or a database, which is an organized collection of saved records.

The agent saves notes in an external store and reads them back by calling tools. That way a fact survives when the host cuts old parts from the transcript or starts fresh. This has costs, because the agent has to choose what to save and what to fetch. A fetch can also miss what it was looking for. A wrong note is also a problem, because the agent trusts it the next time it reads it.

Anthropic's multi-agent research system saves its plan to external memory. Its transcript would be cut off once it passed 200,000 tokens (Anthropic Engineering, June 2025). This lab does not simulate memory at all, so its agent has nothing to work with except the transcript.

### Several agents

A **multi-agent system** has several agent loops working on one job. Often one lead agent is in charge of the others. In one common pattern, the lead agent splits the job and hands pieces to helper agents. Each helper keeps its own transcript, and the lead agent then combines what they send back. That can help when the work splits into parts that run side by side. It can also help when the job is too big for one context window.

It also costs more. Anthropic reported that its agents used about 4 times the tokens of a normal chat. Its multi-agent system used about 15 times. It added that most coding jobs split into fewer side-by-side pieces than research does. It also said that agents are not yet great at coordinating and handing out work in real time.

Every hand-off between agents is one more step that can go wrong. So compounding error applies across a team of agents too. This lab has only one agent, and it simulates none of this.

Sources: Anthropic Engineering, “How we built our multi-agent research system” (June 13, 2025), anthropic.com/engineering/multi-agent-research-system.
