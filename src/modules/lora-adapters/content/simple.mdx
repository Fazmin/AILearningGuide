## The big picture

Picture a model that has already learned from one kind of text. Now you want it to take on a new
job, such as writing recipe steps. The direct way is to keep training every number inside the model
on the new text. The *Fine-tuning & transfer* lab did exactly that.

That works, but each new job leaves you with a full new copy of the model. A large model holds
billions of numbers in every copy.

This module is about a cheaper method called **LoRA**, short for low-rank adaptation. LoRA locks the
original numbers so that training can never change them. It trains a small add-on, called an
**adapter**, and adds the adapter's numbers on top.

Picture the original model as a printed page and the adapter as a clear plastic sheet laid over it.
Whatever is drawn on the sheet changes what you read. The page underneath stays exactly as it was.

Because the add-on stays separate, you can lift it off or swap in another one for a different job.
You can also photocopy the page with the sheet on it into one new page for good. Each choice has a
price, and this lab lets you see every one of them.

### Where it shows up

The calculator in this lab uses the real sizes of three Llama 3 models. These are large language
models, the kind of program behind a chatbot. The smallest has about 1 billion learned numbers and
the largest has about 70 billion.

LoRA is built into the free toolkits people use to adapt models like these. It is also in the
software that companies run to answer chatbot requests. Because an adapter is small, one computer can keep a single copy of a big model. It clips on a different adapter for each request.

The researchers who introduced LoRA compared it with retraining every number of GPT-3. This earlier language model has 175 billion of them. They found that LoRA could cut the numbers you train by
10,000 times.

### Why it matters

Without a method like this, teaching a model ten jobs means storing ten full copies of it. Training
each copy also needs extra working memory for every number. That is because popular training methods
keep notes on each number they are allowed to change.

With LoRA, you store the big model once and each job adds only a small file. For the 8-billion-number
model in the calculator, the starting setting gives an adapter of about 84 megabytes. The model's own
numbers, stored the same way, fill about 16,000 megabytes. So the adapter holds about half a percent
as many numbers as the model itself.

In this lab, the cheap version also fits the new text about as well as retraining everything. That
result is what makes the trade worth making.

### What you will be able to explain

By the end of this lesson, you should be able to explain these ideas in your own words:

- what the add-on, written `B · A`, adds to a table of numbers that stays locked the whole time;
- how the **Rank** setting, the number of patterns the add-on mixes, trades fit against cost;
- what you gain by merging the add-on into the original table for good, and what you give up;
- why a brand-new adapter changes nothing until it is trained, and how it still starts learning;
- how to size a real adapter by numbers trained, share of the model and file size;
- how that size compares with the toy's.

## What it is

### The base model: a table of 900 numbers

The model in this lab reads one character and guesses which character comes next. Its alphabet has 30 characters. They are a space, the 26 letters, a full stop and two spare symbols. The text never uses the two spare symbols.

Everything the model has learned sits in one table. It has a row for each character the model might read. It also has a column for each character that might come next. Each cell holds a score, and a higher
score means that pairing is more likely. In the row for `t`, the cell in the `h` column holds a high score. The training text says "the" again and again.

To make a guess, the model turns one row of scores into chances that add up to 100%. Bigger scores
get bigger chances. These raw scores are called **logits**, a word the lab uses when it checks a
merge.

The table has 30 rows and 30 columns, so it holds 900 numbers. These numbers are called **weights**
or **parameters**, and the lab calls the whole table `W`. A table of numbers in rows and columns is called a **matrix**. So you will also see `W` called a weight matrix.

The table `W` trained for 60 passes over a short text called Harbor weather notes. This text is eight lines about fog, wind, rain and boats. One full pass over the training text is called an **epoch**.

The lab measures how well a model fits a text with a **loss**. The loss is the average of how
surprised the model is by each real next character. The model is very surprised when it gave the real
character a small chance. It is barely surprised when it gave that character a big chance.

Lower is better: a model that spread its guesses evenly over all 30 characters would score about 3.4. So any score below that means it picked up real patterns.

The base model scores 1.921 on Harbor weather notes, the text it trained on. It scores 2.556 on
Recipe steps, a short set of cooking instructions it never saw. It does worse on recipes. Cooking lines such as "simmer the sauce until it thickens" follow different letter patterns from weather notes.

This is the same base model that the *Fine-tuning & transfer* lab starts from, rebuilt inside this
lab. So the two methods begin from exactly the same place.

### Locking the table and adding a correction

Fine-tuning, in the last lab, let training change all 900 numbers in `W` on the recipes. Only 720 of
them actually move, as the note under the lab's formula row points out. The recipes never contain some characters, such as j, q, x and z. So the rows for those characters get no push.

LoRA takes a different route and **freezes** `W`. The model still reads the table for each guess, but training never writes a change into it.

Instead, LoRA learns a separate grid of corrections, the same 30 by 30 size as `W`. The model adds
this grid to the table, cell by cell, before each guess. The lab calls the grid `ΔW`, said "delta W".
The Greek letter Δ is the usual math shorthand for "change in".

The lab's formula row, **Effective weights**, shows the table the model really uses. At the starting
settings it reads `W + (8 / 4) · B · A`, where each dot means "times". That is
`W + (alpha / rank) · B · A` with the two slider values filled in. The part `B · A` is the raw
correction, built from two small tables explained below.

The fraction `alpha / rank` is a dial that turns the raw correction up or down. Two sliders set it, and the grid `ΔW` is the correction after the dial. At the starting settings the dial is 8 ÷ 4 = 2,
so `ΔW` is twice `B · A`.

Picture the base table as a printed page and the **adapter** as a clear plastic sheet laid on top.
Ink on the sheet changes what you read, but the page itself is never marked. When you lift the sheet
off, the original is exactly as it was.

You can keep a different sheet for each job and swap them in and out, which is called
**hot-swapping**. You can also photocopy the page with a sheet on it into one flat new page. This is called **merging**, and the copy is quicker to read because it has only one layer. But you can never peel
the sheet off it again.

### Building the correction from two thin tables

If the correction could be any 30 by 30 grid, it would have 900 numbers of its own. You would be
training as many numbers as before. LoRA saves work by building the grid out of two thin tables, called `B` and `A`. These need far fewer numbers.

In the simplest case, `B` is one column of 30 numbers, one for each row of the grid. The table `A` is
one row of 30 numbers, one for each column. Multiply the `B` number for a cell's row by the `A` number for its column.

This works like a times table, where every cell is its row heading times its column heading. That is
how 60 numbers can fill all 900 cells.

Here is a made-up miniature with three rows and three columns, so you can see the arithmetic. Say `A` holds the pattern 2, 0, −1, and `B` holds one number per row. Each row of the grid is its `B` number times that pattern:

- Row 1 has a `B` number of 1, so it reads 2, 0, −1.
- Row 2 has a `B` number of 3, so it reads 6, 0, −3.
- Row 3 has a `B` number of 0, so it reads 0, 0, 0.

Six numbers filled nine cells, but there is a catch. Every row is the same pattern, multiplied by a
different amount. A correction built from one pattern can only push every row in that one shared way. It pushes harder on some rows and softer on others. A row whose `B` number is negative gets the pattern in
reverse.

To allow more variety, LoRA adds several of these times tables together. With two patterns, `B` gets
a second column and `A` gets a second row. Then every row of the correction becomes its own mix of
the two patterns.

In the miniature, add a second pattern, 0, 1, 1, and give each row a second `B` number. The new numbers are 0 for row 1, 1 for row 2 and 2 for row 3. Each cell now adds two products, one from each pattern:

- Row 1 stays 2, 0, −1, because it takes none of the new pattern.
- Row 2 becomes 6, 0, −3 plus 0, 1, 1, which is 6, 1, −2.
- Row 3 becomes 0, 0, 0 plus twice 0, 1, 1, which is 0, 2, 2.

The rows no longer follow one shape, because each one mixes the two patterns in its own amounts. In a
grid this tiny, two patterns already cost more numbers than the grid holds. In the lab's 30 by 30
grid, each pattern costs 60 numbers against 900 cells. So a few patterns stay cheap.

The number of patterns is the adapter's **rank**, written `r`. The **Rank** slider sets it from 1 to 12. So `B` is 30 tall and `r` wide, and `A` is `r` tall and 30 wide. Multiplying them always gives
a 30 by 30 grid.

In math, the smallest number of patterns needed to build a grid is called its rank. That is where the
name comes from: low-rank adaptation means a correction built from only a few patterns. The lab's
chart calls each pattern a **direction**, so a rank-4 correction has at most 4 directions.

### Counting the cost

Each pattern costs 30 numbers in `B` plus 30 in `A`, so every pattern adds 60 numbers to train. The lab writes this as `r · (d + k)`. Here `d` and `k` are the height and width of the table, both 30. At the starting rank of 4, that is 4 × 60 = 240 numbers to train. That is a little over a
quarter of the 900 that full fine-tuning trains.

A higher rank gives the correction more freedom. It also means more numbers to train, store and load.
The **Rank** slider lets you explore this trade between fit and cost.

### Where the sheet picture stops matching

Ink on a real sheet usually marks a few spots and leaves the rest clear. This sheet is not a small
patch. It can change every cell in any row the recipe text uses. That is 24 of the 30 rows here.
Only the rows for characters the recipes never contain stay exactly as they were.

Nothing on the sheet is a drawing you could read, either. It is a grid of small positive and negative numbers, and you cannot draw on it freely. Everything on it must be built from `r` patterns,
which is exactly the limit that rank sets.

### What the diagram shows

The card called **The low-rank update** draws all of this with the real trained numbers. The table
`A` runs across the top, labelled `A · 4 × 30 · random start`. The table `B` runs down the left, and
the finished correction `ΔW` sits where the two meet.

The label tells you how `A` began. Once training starts, `A` changes too, and after 24 passes most of
what you see in it was learned.

In the `ΔW` grid, blue cells raise a score compared with the rest of their row. Red cells lower it. In `A` and `B`, blue means a positive number and red means a negative one. A deeper colour means the number is further from zero. The lab measures this against the biggest number in the same grid.

Below the diagram, a second map shows the change that full fine-tuning made to the table. It covers the same passes. Any grid, even that one, can be broken into patterns like the ones above, up to 30 of
them. Some patterns carry much more of the change than others.

A chart next to that map asks the same question of both changes. If you kept only the `k` strongest
patterns, how much of the change would you keep? This is the same letter as in the cost formula, but
here it means the number of patterns kept. The solid curve is the adapter, and the dashed curve is
full fine-tuning.

To judge size, the chart squares each number in a change and adds the squares up. That is why it
talks about squared size and update energy. The bottom axis calls each pattern's strength a **singular value**. This name comes from the math used to find the patterns. You will not need that math here.

The adapter's correction is built from exactly `r` patterns. So its solid curve always reaches 100% at k = r and stays flat after that.

### Why a fresh adapter changes nothing

Before any training, `B` is filled with zeros and `A` is filled with small random numbers. In the two-pattern miniature, every cell of `B · A` multiplied `B` numbers by `A` numbers and added the results. Anything multiplied by zero is zero.

So the whole correction is exactly zero, and the effective weights are exactly the base weights.
This starting trick is called **zero initialization**. So training begins from the base model's own behaviour, not from a copy that random numbers knocked off course.

You might wonder how `B` ever moves if it starts at zero. Training looks at a small handful of examples at a time, called a **batch**. It nudges the trainable numbers after each batch. Each number
gets a push that says which way to move to lower the loss. That push is called its **gradient**.

Picture one cell made from a `B` number of 0 and an `A` number of 0.3. The cell is 0 × 0.3 = 0. If
training nudges the `B` number up by 1, the cell becomes 1 × 0.3 = 0.3. So a change to `B` moves the
cell by an amount set by `A`.

Now suppose training nudges the `A` number instead. The cell is still 0 times something, which is 0.
A change to `A` cannot help yet, so training gives `A` no push at first.

That is why `B` starts moving on the very first batch. The table `A` has to wait until `B` holds something other than zero. It is also why the two cannot both start at zero. Nudging either one alone
would leave every cell at zero, and neither would ever get a push.

### What Alpha does

The correction passes through one more control before it is added. That control is a scale equal to
`alpha / rank`, where **Alpha** is a slider from 1 to 24. At the starting settings, **Rank** is 4 and **Alpha** is 8. So the scale is 8 ÷ 4 = 2.00, and `ΔW` is twice `B · A`. The card's top line shows all
three at once, as `rank 4 · alpha 8 · scale 2.00`.

Why divide by rank at all? Adding more patterns together tends to make the raw correction bigger. The
researchers behind LoRA reasoned that dividing by the number of patterns keeps its size roughly
steady. Then training settings that worked at one rank still work at another.

That reasoning was made for a different training method from the one this lab uses. In this lab, the scale also sets how big every training nudge is. So a smaller scale means smaller nudges.

The catch shows up when you hold **Alpha** at 8 and slide **Rank**, because the scale moves too. Rank
1 gets a scale of 8.00, while rank 12 gets only 0.67. So a higher rank also gets a smaller scale. In this lab, that makes each training nudge count for less.

At **Alpha** 8, rank 12's finished correction ends up a little over half the size of rank 4's. When
alpha equals rank instead, the correction stays roughly the same size from rank 4 to rank 12.

Whenever alpha and rank differ, the card shows a warning that the scale has changed. Under it sits a
button labelled **Set alpha = rank, for a scale of 1**, which makes the two equal.

### From the toy to a real model

Real models are built from the same kind of tables, only far bigger and far more of them. Take a model such as Llama 3 8B, where 8B means about 8 billion numbers. It is a stack of 32 **layers**. The layers
are steps that the text passes through one after another, and each layer holds several weight
matrices.

Four of them sit in the attention part from the *Attention* lab. They are named `q`, `k`, `v` and
`o`, for query, key, value and output. Here `k` is only the name of a table, the third job this
letter has had in the lesson. Three more tables sit in a second part called the **MLP**. This block works on each position of the text after attention has run. The calculator names those three gate, up
and down.

Every one of these tables has the **model dimension**, `d`, as at least one of its sides. The letter
`d` stands for how many numbers the model uses to describe each piece of text. For Llama 3 8B, `d` is 4,096, and the calculator uses `d` for this width only. In the toy's cost formula, `d` and `k` were the table's two sides.

The tables are not all square, though. In Llama 3 8B, `q` and `o` are 4,096 by 4,096, but `k` and `v`
are 4,096 by 1,024. The three MLP tables are 4,096 by 14,336, with down turned the other way round.
That is why the MLP takes most of the adapter.

Choosing which matrices get adapters is called picking the **target modules**. The calculator's
**Target matrices** buttons do exactly that. There is one button for each attention matrix and one
for the whole `MLP`.

For each targeted matrix, the adapter pair costs `r · (inputs + outputs)`. Here inputs and outputs are the matrix's two sides. The calculator's formula row adds that up over all targeted matrices and
layers. It writes the sum as `Σ r · (inputs + outputs)`, where the Greek letter Σ means "add them all
up".

Here is a worked example. The `q` matrix in Llama 3 8B has 4,096 inputs and 4,096 outputs. Its two sides add up to 8,192. At rank 16, one layer's pair for that matrix holds 16 × 8,192 = 131,072
numbers. Across all 32 layers, that comes to 4,194,304. This is the figure the calculator's bar list
shows for `q projection`.

The same steps work for the other tables. For `k`, the sides add up to 4,096 + 1,024 = 5,120. So 32
layers at rank 16 give 16 × 5,120 × 32 = 2,621,440. Each MLP table has sides that add up to 18,432. So the three of them come to 28,311,552, about two thirds of the whole adapter.

Add `q` and `o` at 4,194,304 each, `k` and `v` at 2,621,440 each, and the MLP. The total is
41,943,040, which is the count the calculator shows for every matrix at rank 16.

### From a count to a file size

To turn a count into a file size, you need to know how much room each number takes. Computers store
everything as **bits**, and each bit is a single 0 or 1. Eight bits make one **byte**.

At an **Adapter precision** of 16-bit, each number takes 16 bits, which is 2 bytes. A **megabyte**,
written MB, is a million bytes, so a million numbers stored at 16-bit fill 2 MB. More bits per number
keep each number more precise, but they make the file bigger in exact proportion.

So the 8B adapter's 41,943,040 numbers, at 2 bytes each, fill 83,886,080 bytes. That is the 83.9 MB
the calculator shows.

### Why a real adapter is a tiny share

Last, the calculator divides the adapter's count by the number of weights in the whole base model. It
shows the result as **Share of the base model**. The badge at the top of the card gives the 8B
model's count, about 8.03 billion. Then 41,943,040 ÷ 8,030,000,000 is about 0.00522, or 0.522%.

The general name for this is the **trainable fraction**. It is how many numbers training may change,
as a share of how many the base model holds. With LoRA, the numbers training changes are the
adapter's. The lab says the toy "trains 26.7% of its table". That means the adapter holds that many numbers compared with the table. The table itself still never changes.

A pair's cost grows with the *sum* of a matrix's two sides. The matrix itself grows with their *product*. In the times-table picture, 60 headings fill a 900-cell table. But 8,192 headings fill a
table of more than 16 million cells.

So the bigger the matrix, the smaller the adapter's share. You can see this by comparing two matrices
at rank 4. The toy's adapter holds 26.7% as many numbers as its 30-wide table, a bit more than a
quarter. Take a 4,096 by 4,096 matrix at the same rank. It needs 4 × (4,096 + 4,096) = 32,768 adapter numbers, while the matrix itself holds 16,777,216. That makes the adapter only 0.195% of it, or about
1 number in 500.

## Why it’s here

With LoRA, the base table stays exactly as it was, byte for byte. The only new thing you keep for
each task is the adapter, which is 60r numbers in this lab.

The saving reaches training as well as storage. A popular training method keeps two extra numbers of
notes for every number it may change. At rank 4, that bookkeeping covers 240 adapter numbers instead
of all 900. The frozen table needs none at all.

Picture a school with one expensive set of science textbooks and three teachers. Each teacher wants
to mark up the books for their own class. Suppose every teacher buys and marks up a full set. The school pays for three sets and fills three shelves.

Suppose each teacher keeps a thin folder of clear sheets that lie over the pages. Then the school
keeps one set of books and three thin folders. A teacher can also lift her sheets off at the end of a lesson. The next class then finds the books exactly as they were.

The open question is whether squeezing the correction into a few patterns costs too much accuracy. In
this lab it costs almost nothing. With 24 passes, a rank-4 adapter with 240 trained numbers reaches a loss of 2.077 on Recipe steps.

Retraining all 900 weights for the same 24 passes reaches 2.090. So here the adapter does slightly
better while training a little over a quarter as many numbers. That is one measurement on one small text. Treat it as an example of the trade, not as a rule.

Why might a cheap correction do about as well? LoRA rests on a bet that the *change* a new task needs is simple. The table being changed is not simple. Recipes push the model to favour some letter pairs over others. One example is `a` after `s` for "sauce" and "salt". The bet is that a handful of
patterns can carry most of a shift like that.

## How to play with it

The lab follows the steps below in order. Each one tells you which control to move and what to
compare.

### Size the update

On **The low-rank update**, drag **Rank** from 1 to 12 and watch `B` widen and `A` grow taller. Each new pattern adds a column to `B` and a row to `A`. The two thin tables grow together.

The slider's label shows the cost as you go, such as `4 · 240 weights`. Below it, the bar list called **Trainable parameter count** compares two bars. One is LoRA at the current rank, and the other is the 900 weights of **Full fine-tuning**. As you drag, the LoRA bar climbs in steps of 60:

- At rank 1, the LoRA bar reads 60 weights, which is one fifteenth of the full table.
- At rank 2, it reads 120, because two patterns cost 60 numbers each.
- At rank 4, the starting value, it reads 240, a little over a quarter of the table.
- At rank 8, it reads 480, which is already more than half of the full table.
- At rank 12, the top of the slider, it reads 720, which is 80% of the full table.

The slider stops at 12, well short of rank 15. At rank 15, the adapter would cost 900 numbers, as many as the whole table. Before moving on, set **Rank** back to 4, its starting value.

### Train the adapter

**Try this:** Set **Adapter epochs** to 0, where the slider reads `untrained`. Then `B` and `ΔW` go
blank in the diagram, even though `A` still shows its random colours. Zero times anything is zero.

**Target loss**, on the **Hot-swap and merge** card, now reads 2.556, which is exactly the base
model's score. Every pair of bars under **Next character after** matches too, because an untrained
adapter changes nothing at all. You will explore those base-versus-adapter bars in a moment.

Now raise **Adapter epochs** back to 24 and look at the **Adapter training loss** chart. Its solid
line peels away from the dotted line, which marks the frozen base model's score on recipes.

The solid line is bumpy because each point averages the loss on about a dozen small batches. The lab measures them while the adapter is still changing. For a fair score, read the full-text loss in the note under the
chart.

The chart measures loss in nats per character. A nat is the unit this surprise score is counted in, the way points count a game score. Every loss in this lesson uses nats. Lower is better,
and the dotted line at 2.556 is the score to beat.

Next, pick `s` under **Next character after**. You will see a row for each of the seven most likely
next characters, each with two bars. The upper, hatched bar is the base model. The lower, solid bar
is the base model plus the adapter.

Find the row for `a`, which reads `5% → 29%`. The base model gives `a` a 5% chance after `s`, and the
adapter raises it to 29%. That fits the text, because recipes keep saying "sauce", "salt" and
"salted".

Now pick `␣`, the symbol the lab uses for a space. The most likely next character, `t`, barely moves,
from 22% to 18%. The picker offers five starting characters: `␣`, `e`, `s`, `l` and `a`.

If you click through all five, the bars after `l` change most. A space after `l` jumps from 5% to 62%. The bars after `s` and `a` change next most, and those after `e` change a little less. The
bars after the space barely move.

### Compare ranks fairly

Keep **Adapter epochs** at 24 and slide **Rank** again. This time, read the target loss printed on
the LoRA bar, where lower is better:

- Rank 1 scores 2.462, the worst of the five and the closest to the untrained model.
- Rank 2 scores 2.316, a clear step better than rank 1.
- Rank 4, the starting value, scores 2.077, which beats full fine-tuning.
- Rank 8 scores 1.990, the best fit of the five.
- Rank 12 scores 2.059, which is worse than rank 8 even though it has more patterns.

That last result looks odd until you read the warning above the bars. It says that with **Alpha**
held at 8, the scale changed every time you moved **Rank**.

At each rank, press **Set alpha = rank, for a scale of 1** so that the scale reads 1.00. Then read the loss again, and notice that the extra patterns now pay off. Rank 12 comes out slightly ahead of rank 8.

Rank 4 is worth a look here too. The button drops its scale from 2.00 to 1.00. Its loss rises to 2.091, level with full fine-tuning's 2.090. So the adapter's small win at the starting settings owes
something to its scale.

The button disappears once the two values match. It comes back as soon as you move **Rank** again,
because **Alpha** stays wherever you left it.

Before moving on, set **Rank** back to 4 and **Alpha** back to 8. The next steps quote the numbers
for those starting values.

### Hot-swap it

On **Hot-swap and merge**, flip **Serving** between `Base only` and `Base + adapter`. Watch three
readouts move together:

- **Target loss**, the score on the recipes, moves between 2.556 and 2.077.
- **Source loss**, the score on Harbor weather notes, moves between 1.921 and 2.235.
- **Serving weights** moves between 900 and 1140. Keeping the adapter separate means holding its 240 numbers beside the table.

The sample text under the readouts changes too, because whichever table is being served writes it.
The model gets the word "the" and a space to start from, but that start is not shown. So the text
begins with what the model wrote next. It uses a temperature of 0.7, a setting that controls how much
randomness goes into picking each character.

### Merge it

Press **Merge the adapter into W**. The button changes to `Adapter merged into W`, and **Serving**
shows only one option, `Merged — nothing left to swap`.

**Serving weights** drops back to 900, because the correction now lives inside the table itself.
**Target loss** stays at 2.077, since the merged table holds the same numbers the adapter was
producing.

In a real system, an unmerged adapter makes every guess take extra work. The model reads its row of `W` and builds the matching row of the correction from `B` and `A`. Then it adds the two, but after a merge that sum is already done and stored. Each guess reads one table, and that saved work is what merging
gains.

The callout under the button reports the largest logit gap, at about 4e-7, which is 0.0000004. This
is the biggest difference in any score between the merged table and the unmerged path. The unmerged
path keeps `W` and the adapter apart and adds their effects for each guess. Changing **Rank**,
**Alpha** or **Adapter epochs** undoes the merge, because each of them retrains the adapter.

### Size a real adapter

Open the **Adapter size calculator**, which starts on **Architecture** `Llama 3 8B`. Every button under **Target matrices** starts on, and **Adapter rank r** starts at 16. At those settings, the three
readouts across the middle of the card show what the adapter costs:

- **Trainable parameters** reads 41,943,040, the count of numbers the adapter would train.
- **Share of the base model** reads 0.522%, which is about 1 number in every 190.
- **Adapter size at 16-bit** reads 83.9 MB, the size of the file that holds those numbers.

Switch the `MLP` button off, and the count falls to 13,631,488, or 0.170% of the model. Switch the `MLP` back on, then set **Adapter precision** to `32-bit`. This stores each number with twice as many bits. The size doubles to 167.8 MB, since each number now takes 4 bytes instead of 2.

Then read the callout at the bottom of the card. It uses the **Rank** from the first card, not the
calculator's own rank. At the toy's starting rank of 4, it says the toy trains 26.7% of its table. The 8B model with every matrix targeted trains 0.131%.

That is lower than the 0.522% above because the callout uses rank 4, a quarter of 16. So the share is
a quarter as big.

Last, switch **Architecture** between `Llama 3.2 1B`, `Llama 3 8B` and `Llama 3 70B`. Watch **Share
of the base model** fall as the model grows.

## What to notice

### The cheap adapter keeps up

- **The headline:** 240 trained adapter numbers matched 900 trained weights at the same budget, 2.077
  against 2.090. That is the case for adapters, measured once on one small text.
- **A spread-out change:** Full fine-tuning got there with a change spread over many patterns, not a
  simple one. On the chart, its first 4 directions hold only 63% of that change.
- **More directions:** Even its first 8 directions hold only 86%. Its dashed curve does not pass 95% until it reaches 11.
- **What that means:** A rank-4 adapter holds at most 4 directions. At best, it could copy 63% of full fine-tuning's change, yet it still scored as well. So it must have found a different, simpler change that fits recipes about as well.

### More rank is not automatically better

At **Alpha** 8, rank 8 gave the best recipe loss of the five listed ranks, not rank 12. If you stop at every rank, rank 7 is best at 1.977. Rank 12 does worse than every rank from 5 to 11.

Two things changed at once, and that is the problem. Rank 12 had more patterns to work with, but its
scale had dropped to 0.67. That smaller scale made every push it took count for less.

Picture testing whether bigger study groups score higher on a quiz. Each time you add a member, you cut the study time. If the biggest group does worse, you cannot tell whether the size hurt or the
shorter session did. The rank sweep at a fixed **Alpha** has exactly that problem. Setting alpha
equal to rank fixes it by holding the scale at 1.00.

So a worse score at rank 12 does not prove that extra rank harms the fit. Once the scale is held at
1.00, rank 12 edges ahead of rank 8. The drop came from the weaker scale, not from the extra
patterns.

### Swapping and merging

- **Detaching:** Taking the adapter off restores the base exactly, because `W` was never written. So
  **Source loss** goes back to 1.921.
- **Forgetting:** While the adapter is on, the model does worse on Harbor weather notes than full
  fine-tuning left it. It scores 2.235 there against full fine-tuning's 2.088.
- **The scale:** A scale of 2.00 makes the adapter's correction bigger, but it is not the main reason.
  Set **Rank** to 4 and **Alpha** to 4 for a scale of 1.00. The adapter now fits recipes as well as full fine-tuning, 2.091 against 2.090. Yet it still leaves Harbor weather notes at 2.208.
- **The cause:** To reach its recipe score, the adapter's correction grew bigger than full fine-tuning's change. Some of that correction also reaches the harbor text. The lab does
  not pin down the exact cause.
- **Merging:** **Merging** matches the unmerged path to within about 4e-7 per score. That difference
  is rounding, and the recipe loss is the same to four decimal places.

The rounding happens because the unmerged path does its sum with extra-precise numbers each time. The
merged table stores every number once, in a format that keeps fewer digits. The difference is far too
small to change any prediction, which is why the two losses match.

### Real models

- **The gap:** The toy makes LoRA's share look about 200 times bigger than it is on a real model. At rank 4, the toy's adapter holds 26.7% as many numbers as its table. The 8B model's
  adapter, with every matrix targeted, holds 0.131% as many as the model.
- **The trainable fraction:** This is the share being compared. It shrinks on big models because pairs grow with the sum of a matrix's sides. Matrices grow with the product.
- **Targets matter:** Which matrices you target matters as much as rank. At rank 16, the MLP holds 67.5% of the 8B model's adapter. Its three matrices are much larger than the attention ones.
- **Adding the MLP:** Start from `q` and `v` alone at rank 16. Switching on the MLP as well multiplies
  the count by 5.15.
- **Size scales evenly:** Size grows in exact proportion to rank, to layers and to bits. Doubling any
  one of them doubles the file.

The share also falls as the whole model grows. The calculator shows this at rank 16 with every matrix
targeted:

- **1B model:** The adapter is 0.912% of the model, a little under 1 number in 100.
- **8B model:** The adapter is 0.522% of the model, about 1 number in 190.
- **70B model:** The adapter is only 0.294% of the model, even though it holds 207,093,760 numbers.

The same arithmetic also matches a published figure. For Llama 3.2 1B with only `q` targeted at rank
8, it gives 524,288 trainable parameters. That is the exact count printed by the quick tour of PEFT for the same setup. PEFT is a free toolkit for adapting models.

## Where it breaks

### What this lab simplifies

The lab computes everything for real as you move the controls. That covers the adapter, its gradients, both losses, the charts and the merge check. The biggest gap is that this model has only one matrix. So the list of **target modules** has one member. A real LoRA attaches to chosen matrices inside each layer. It often picks `q` and `v`, and sometimes all four plus the MLP. Choosing them well is much of the real skill.

Both `ΔW` maps subtract each row's average before drawing, which the diagram notes as "each row's
mean removed". Adding the same number to a whole row of scores changes no prediction. The chances depend only on how the scores in a row differ from each other.

For example, scores of 2, 1 and 0 give the same chances as 5, 4 and 3. Only the gaps between them matter. Full fine-tuning never adds a same-for-the-whole-row amount, but the adapter
does. So its raw correction is slightly bigger than its map shows. The hidden part is small: at most
about 0.08 per row, next to cells as large as about 4.5.

**Rank** stops at 12, well short of rank 15. At rank 15, the adapter would cost as many numbers as the whole table. The full fine-tuning bar and map come from one run, with one fixed random order of practice
examples. They are a reference point and not a verdict on which method wins.

Nothing is held out. The adapter trained on eight recipe lines, and the lab measures every recipe loss on those same lines. **Source loss** uses the Harbor lines the base trained on. So a low recipe score shows how well the adapter fits those lines. It does not show how the adapter would handle new ones.

Picture a student who is only ever graded on the eight practice questions they studied. A good score
there tells you little about how they would do on new questions. This lab only ever shows you that
practice score.

The training rule is plain SGD. It nudges each number by its gradient times a fixed step size of 0.6. It also uses no dropout. Dropout is a guard that randomly blanks out some of the adapter's inputs during training to discourage memorising.

**Next character after** offers five starting characters, chosen because recipes change them
visibly. Every row whose character appears in the recipes is trained as well. On **Hot-swap and
merge**, there is no second adapter to swap in, so detaching is the only swap.

Merging there is a switch plus a real numerical check, not a new file being written. To keep the lab quick, the `Base + adapter` setting also reads from a table added up in advance. So you
never feel the extra work of an unmerged adapter here. The lab does the slower, separate sum only for
the merge check.

**Serving weights** still counts `A` and `B`, though. That is the memory a real server pays to keep
the adapter swappable.

The **Adapter size calculator** does arithmetic and nothing else. Because it trains and serves
nothing, it cannot tell you whether a given rank is enough for a task. Its `Custom` model follows
Llama 3's proportions and is not a real published model. Its counts leave out anything beyond the
LoRA pairs. All three presets come from one family of models, so a model built differently would give
different counts.

**A common mix-up:** LoRA does not protect a model from forgetting its old job. The rank-4 adapter
leaves Harbor weather notes at 2.235, while full fine-tuning leaves them at 2.088. What LoRA protects
is the base *weights file*, which is why you can swap adapters and merge them.

In the sheet picture, the page under the sheet is untouched. Yet while the sheet is on, the whole page
reads differently, including the parts you never meant to change. Whether the old *behaviour*
survives depends on the scale, the rank and the training budget. Forgetting after full fine-tuning
depends on how long and how hard it trains in the same way.

### Where real LoRA falls short

How close an adapter comes to full fine-tuning depends on the task. Adapters fall behind on big shifts. Examples are a new language, a new kind of input or genuinely new knowledge. Only testing on
examples held back from training tells you which case you are in.

An adapter's training loss can look excellent while the adapter fails on prompts unlike the ones it
trained on. The **Source loss** readout is this lab's cheap check for side effects on the old job.

Serving many unmerged adapters at once needs special code. This code handles several requests together, so no request slows down. Merging several adapters into one base makes them get in each other's
way. That is the subject of the next lab, *Model merging*.

The file on disk also depends on the number format of the adapter. This can differ from the base model's. Even when the base model uses 16-bit numbers, PEFT keeps the adapter's numbers at 32-bit by default. Training is steadier that way, so the 32-bit size is a realistic size
during training. A small trainable fraction also says nothing about quality on its own.

## Going deeper

### The bet behind the method

LoRA's central bet is that the *change* a fine-tune needs is simple, even when the weights are not.
In math terms, the change is close to low rank, so squeezing it into rank `r` loses little.

The squeeze also acts as a brake on overfitting. Overfitting means fitting the training text so
closely that new text suffers. That is part of why small ranks sometimes do better than large ones on
new text. This lab cannot show that, because it scores only the text the adapter trained on.

### Why Alpha divides by rank

The product `B · A` is a sum of `r` one-pattern pieces. So its size tends to grow as `r` grows. The
LoRA paper divides by `r` to hold it roughly steady. Then you can change rank without also changing
how hard the adapter pushes.

That reasoning was made for the paper's training method, Adam. It does not hold for this lab's plain
nudges. Here, alpha equal to rank keeps the size roughly steady, at least from rank 4 to rank 12.

Later work called rsLoRA argues that dividing by the square root of `r` is steadier at large ranks.
PEFT offers that choice as `use_rslora`.

### Where the real saving is

The biggest saving in real systems is training memory, not prediction speed. Adam is the training method from *Why it’s here*. It keeps two extra numbers of notes for every *trainable* weight.
The frozen table needs no notes at all, so its memory goes only to holding it.

### QLoRA

**QLoRA** goes further by storing the frozen base in 4-bit numbers instead of 16-bit. That cuts the
base's memory about four times. The model expands each 4-bit number back to 16-bit on the fly whenever a multiply needs it. Only the 16-bit adapter trains.

That was enough to fine-tune a model with 65 billion numbers on one graphics chip. This chip, or GPU, had 48 gigabytes of memory, and a gigabyte is a billion bytes.

The *Quantization* lab shows the plain version of this storage trick, where the allowed values are
evenly spaced. QLoRA's 4-bit format is called NormalFloat or NF4. It spaces its 16 allowed values
unevenly, to suit weights whose values follow a bell-shaped spread. The QLoRA paper calls this layout the best possible use of 16 values for such weights. It means best in a precise mathematical sense.

A second trick, called double quantization, squeezes the small helper numbers that the 4-bit format
needs. That saves a little more memory.

### Older adapters

Earlier **adapter** designs slid small extra layers between the frozen ones. Those extra layers stay in every prediction forever, but LoRA's correction is plain addition. So you can fold it into `W` once, and it costs nothing extra when the model makes predictions.

An adapter that does anything beyond multiplying by fixed numbers and adding cannot be folded in this
way. Cutting off negative values is one example.

### Other ways to adapt

LoRA is one member of a family called **PEFT**, short for parameter-efficient fine-tuning. It means
training a small set of added or chosen numbers while the base stays frozen. The PEFT toolkit,
published free by the company Hugging Face, collects these methods. They differ in what is trained
and where:

- **Prompt tuning** trains a few extra lists of numbers, called soft prompts, that are added to the
  model's input.
- **Prefix tuning** also trains lists of numbers. It slips them into every layer, not only at the input.
- **IA3** learns numbers that turn the volume up or down on parts of each layer. PEFT's guide says it
  trains about 0.01% of a model called T0, where LoRA trains more than 0.1%.
- **DoRA** splits each weight into a size and a direction. It adapts the direction with LoRA and
  learns the size separately. PEFT turns it on with `use_dora` and recommends merging it before use,
  because it adds extra work.

### Serving many adapters

Because an adapter is small, one server can hold a single copy of the base model and many adapters. It then picks one for each request, which is called **multi-adapter serving**. It works like keeping one
printed page and a stack of clear sheets beside it.

PEFT's quick tour shows the simplest version. There, `add_adapter` registers a named adapter and
`set_adapter` switches to it. The serving software vLLM runs LoRA adapters when you start it with `--enable-lora`. Each request names the adapter it wants. A setting called `max_loras` caps how
many adapters run at once.

The S-LoRA paper describes a system that keeps every adapter in main memory. It moves the ones in use onto the GPU. It reports up to four times the work done per second of vLLM and PEFT setups. It does that while serving several orders of magnitude more adapters. Each order of magnitude means ten times as many.

A merged adapter gives all of this up, because each merge is a separate full copy of the weights.

### Toy versus real

- **Shares:** The toy trains 26.7% of its weights at rank 4. The PEFT quick tour prints 524,288 trainable numbers. That is a rank-8 adapter on the `q` matrices of Llama 3.2 1B.
- **A tiny share:** That quick-tour adapter is 0.0424% of the 1,236,338,688 numbers PEFT counts. That is about 1 number in 2,400.
- **GPT-3:** This is the 175-billion-number model from the start of this lesson. The LoRA paper compares LoRA with retraining all of it using Adam. It says LoRA can cut the numbers being trained by 10,000 times.
- **Settings:** The toy uses ranks 1 to 12, **Alpha** 8 by default and plain SGD. The QLoRA paper used
  rank 64, alpha 16 and adapters on every matrix. Its step sizes, called learning rates, cannot be
  compared with the toy's 0.6.
- **Scale:** The PEFT quick tour's example uses rank 8 with alpha 32, so its scale
  is 4.
- **Files:** PEFT saves an adapter as two files. One is a small settings file, and the other holds the numbers in a format called safetensors. Safetensors is built to store tables of numbers safely and load them
  fast.
- **File size:** The quick tour's adapter for a model called opt-350m is 6.3 MB. The model itself is about 700 MB.
- **Tools:** PEFT's `merge_and_unload` folds an adapter into the base. The training tools in a toolkit
  called TRL work with PEFT.
- **The reverse:** A tool called mergekit can pull a low-rank adapter out of a fully fine-tuned model. The adapter approximates the change.

The base model here trained for 60 passes. The *Model merging* lab trains its own Harbor base for 48 instead. Each lab fixes its own count, and none of them tests the difference.
